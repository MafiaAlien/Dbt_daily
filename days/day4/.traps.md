## Trap 1 — generic tests are blind to NULL (the designated silent failure)

**Clauses:** C11, C12.

`accepted_values`, `relationships` and `unique` all evaluate to "no failing row" on a
NULL, for two different mechanical reasons:

- `accepted_values` compiles to `where value_field not in ('USD','EUR','GBP')`.
  `NULL not in (...)` is NULL, not TRUE, so the row is never returned. `L012`'s missing
  currency is invisible to it.
- `relationships` compiles a child CTE containing `where payout_id is not null`.
  It asserts "a value that appears must exist upstream" and says nothing about whether
  a value appears at all. `L011` is invisible to it.
- `unique` likewise filters nulls before grouping.

Only `not_null` addresses the NULL case, and it must be written separately.

**Naive solution:** covers C11 with a single `relationships` test and C12 with a single
`accepted_values` test, reasoning that each clause got a test. Result: `WARN=1`
(relationships only) instead of `WARN=3`. Build green, contract silently unenforced on
two of the three defective rows.

**What catches it:** the stated `WARN=3` in the pass condition. This is deliberately
given — an undiscoverable trap teaches nothing — but the derivation is his: which three
assertions, on which columns, and why two of them are `not_null` rather than the test
that "looks like" it covers the clause.

**Second-order:** the tempting way to reach `ERROR=0` after writing `not_null` at default
severity is to filter the bad rows out of `stg_d4_payout_lines`. C11 and C12 forbid it in
writing, and Expected Output does not move if he does it (the orphan and null-payout rows
join to no seller either way) — so **this particular wrong fix is invisible in the mart**.
It shows up only as `WARN` dropping below 3, and in the coverage table. Check the staging
model for a `where` clause during review even if every number matches.

**Recurrence:** this is the Day 1 key takeaway ("`relationships` compiles a
`where <column> is not null` into the child CTE; it never asserts the value exists")
tested for retention 3 days later, on a column where forgetting it costs a live defect.

## Trap 2 — the blanket rule "`accepted_values` always pairs with `not_null`"

**Clause:** C13, `payment_method`.

Trap 1 rewards pairing `not_null` with `accepted_values` on `stg_d4_payout_lines.currency`.
`payment_method` is the adjacent column, also `accepted_values`, and there the pairing is
**wrong**: C13 states in bold that the absence is expected behaviour, not a defect.

**Naive solution:** having just learned the pairing on `currency`, applies it to
`payment_method`. `not_null` fires on `L003` and `L007` → `ERROR=2`, build red.

**What catches it:** the failing test, immediately. This is the day's designated
*failing-test* trap. It is recoverable in thirty seconds by re-reading C13, which is the
point — the cost is small, the lesson is that the rule is per-column and lives in the
contract, not in a habit.

**Recurrence:** this is a direct, deliberate re-run of the blindspot first named on
Day 3 — *"[general] Substituting a blanket rule for case-by-case reasoning"* (Day 2's
uniform `else 0` across a count and a sum; Day 3's `{{ config() }}` written into all six
models "no matter how they are set in dbt project yaml"). Third occurrence if he hits it.
Two adjacent columns, same generic test, opposite correct answers, both stated
explicitly in the contract — the only way through is to read the clauses one at a time.

## Trap 3 — singular tests that are too broad

**Clauses:** C15, C16. Both are qualified; the qualifier is easy to drop.

**C15** — "every **PAID** payout has at least one line." Drop `PAID` and the test returns
`P1004` and `P1007`, two `PENDING` payouts that legitimately have no lines yet →
`ERROR=2`, build red on rows that are not defects.

**C16** — "for every payout **that has at least one line**, amount equals the sum of its
lines." Two failure shapes, and they are not symmetric:

- With `coalesce(sum(line_amount), 0)` and no scope filter: `P1004` (750.00 vs 0) and
  `P1007` (300.00 vs 0) are returned → `ERROR=2`, build red. **Loud, and therefore the
  good outcome.**
- Without the `coalesce` and no scope filter: `750.00 <> NULL` evaluates to NULL, the row
  is not returned, and the test **passes for the wrong reason**. The suite is now green,
  the scope bug is still there, and nothing in the run says so. Silent.

The second shape is the one to look for in review. A green C16 test is not evidence the
clause is enforced — read the SQL and check whether an inner join, a `having count(...)
> 0`, or an explicit `where exists` does the scoping, or whether NULL comparison is doing
it by accident.

**Recurrence:** the NULL-in-a-predicate mechanism is the same one that produced Day 3's
`is_billable is not null` (a null check that filters nothing). New surface: the NULL bug
is now inside *his own test* rather than inside a model, which is worse — a broken test
does not fail, it just stops protecting anything.

## Not a designed trap — recurrence watch: fan-out in the mart

`fct_d4_seller_payouts` carries `payout_count` (grain: payout) and `line_count`
(grain: line) in one row. `stg_d4_payouts LEFT JOIN stg_d4_payout_lines` followed by
`count(*)` inflates `payout_count` by each payout's line count.

Wrong values if he does it: SL01 `payout_count` 5 instead of 2, `paid_payout_count` 5,
`paid_amount` 5831.00 instead of 2240.50; SL02 4/3/6300.00 instead of 2/1/2100.00; SL03
2/1/640.00 (unchanged — one line each, so this seller hides the bug); SL04 unchanged.

**No test in the suite catches this** — `not_null` and `unique` on `seller_id` all pass.
Only Expected Output catches it. If it happens, it is the **fourth** occurrence of
*"[modeling] Counting at a grain that is not the entity being counted"* (Day 1 trap 3,
Day 2 trap 1, Day 3's `subscriptions LEFT JOIN usage_events` fan-out), and the first one
where he was warned in the problem text — the mart spec says in as many words that the
two counts are at two different grains and to decide where each is aggregated before
writing the join. Escalate hard if it recurs after an explicit warning.

Note also `SL04`: one `PENDING` payout, `paid_amount` must be `0.00` and not NULL. Fourth
run of the `sum()`-over-an-empty-set lesson from Day 1.
