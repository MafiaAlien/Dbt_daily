- Key takeaways:
  - 四个内置 generic test 里，只有 `not_null` 回答"值在不在"，其余三个只回答"值对不对"，且排除 NULL 的机制不同：`unique` 和 `relationships` 的编译产物里**明写**着 `where <column> is not null`（前者不让 NULL 参与唯一性，后者只断言"出现过的值必须在 parent 存在"），而 `accepted_values` 靠三值逻辑 —— `NULL not in ('A','B')` 求值为 NULL 而非 TRUE，被 `WHERE` 挡掉。所以一列的完整合约通常要拆成两个断言，而且两个断言可以有各自的 severity：同一列上 `not_null` 设 warn（已知缺陷、必须报不许拦）+ `accepted_values` 留 error（真出现非法值就 fail）。
  - `severity` 是天花板，不是默认值。dbt 源码 `task/test.py` 里判定只有一条路径能 fail：`if severity == "ERROR" and result.should_error`。所以 `severity: warn` 配上 `error_if: ">10"`，`error_if` 被完全架空，永远最多是 WARN;阈值写法必须建立在 `severity: error` 之上（`severity: error` + `warn_if: ">0"` + `error_if: ">10"`）。另外 severity 只在测试**返回了行**之后才被咨询 —— 返回 0 行时 error 和 warn 没有任何区别，改 severity 治不了"测试根本抓不到这一行"。
  - 自定义 generic test 的**目录决定了 dbt 怎么解释这个文件**：定义只在 `macros/` 和 test-path 根下的 `generic/`（即 `tests/generic/`）被识别，放进 `tests/dayNN/generic/` 这样深一层的目录不算。放错的后果有两层，且都不在 parse 阶段暴露 —— 文件被当成 singular test，`{% test %}` 块只是定义、不输出任何文本，渲染成空字符串后被塞进 `select ... from ( ) dbt_internal_test`，报 `syntax error at or near ")"`；同时每一条引用它的断言在**执行**时各自变成一个 `'test_xxx' is undefined` 的 Compilation Error。`dbt compile` 打出空的编译产物，就是这个形状的指纹。
- Recurring-pattern check: four repeats, two escalations, and one pattern that did **not** repeat. (1) The fan-out is the **fourth occurrence** of counting at a grain that is not the entity being counted — Day 1 trap 3 (null-padded row counted), Day 2 trap 1 (same family on the dedup side), Day 3 (`subscriptions LEFT JOIN usage_events` inflating two dimension counts), and now this. It is the first occurrence where the problem text warned him in advance, in as many words: "*`payout_count` and `line_count` are counts of two different things at two different grains… Decide where each one is aggregated **before you write the join**.*" Day 3's key takeaway states the correct two-stage shape explicitly. Blindspot entry escalated: the failure is no longer knowledge, it is sequence — the grain of each metric must be written down before the `from` clause is. (2) `payment_method` is the **third occurrence** of substituting a blanket rule for case-by-case reasoning — Day 2's uniform `else 0`, Day 3's `{{ config() }}` in all six models, and now `not_null` beside every `accepted_values`. The day was designed so that two adjacent columns, same generic test, have opposite correct answers, both stated explicitly in the contract; blindspot entry sharpened. (3) `days/day4/notes.md` left at three bare headings and an empty table header — **fourth occurrence**, third consecutive day with the whole file empty. This day it cost more than the others: the `## Contract coverage` table was itself a graded deliverable, and filling one row per clause would have surfaced trap 2 (C13 must have exactly one test and no `not_null`) and the missing `country` `not_null` without any help from execution. (4) New pattern, first named this day: **modifying the graded artifact after seeing execution results.** `models/day4/staging/schema.yml` was written at 15:33:52, after the manifest of the review's own build at 15:32:58, adding `severity: warn` to the `relationships` that had just failed; its `currency` block also differs from what was read in phase 1. Day 4's code is untracked in git, so no pristine copy exists — the review was graded against the executed snapshot, reconstructed from the build output, the manifest severities and the phase-1 file dump. This is the same discipline as "verdict committed before verification", applied to the solution rather than the review. **Not repeated this day:** "could not settle by reading: none" written alongside an admission of uncertainty — the verdict contains no such admission, so for the first time in four days that line is not self-contradicting. The problem is now the opposite one: nothing was left unsettled because almost nothing was examined.
