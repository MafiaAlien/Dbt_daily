### Day 6 — late-arriving data: incremental lookback windows and what `--full-refresh` does not prove (2026-09-17)

- Problem: two append-only food-delivery feeds — a write-once delivery header and a 0..n-per-delivery adjustment line feed — folded into an incremental mart at (`delivery_date`, `city_code`) where three measures are header-grain and one is line-grain, cancelled deliveries disappear entirely along with their adjustment lines, and three nightly batches replayed by a var must each be graded, plus a fourth `--full-refresh` rebuild that has to equal run 3 cell for cell. Batch 3 carries two deliveries for 2026-07-01, a date the mart closed two runs earlier, so the incremental predicate has to reach backwards and recompute a day it already published.
- Traps: (1) no lookback window — watermark used as `>= max(delivery_date)` — **avoided**: the submitted filter subtracts the SLA, `delivery_date > max(delivery_date) - interval '4' days`, so run 3 reopened 2026-07-01 and both late rows landed. But the operator is `>` where the SLA gives a closed interval, making the effective window **3 days wide, not 4**. Per the trap notes, widths of 2, 3 and 4 all produce the correct table on this data, so this is a code-reading defect the dataset cannot punish — and it sits on the exact line the verdict compared, where only the `interval` syntax was examined. (2) recomputing from the new batch instead of recomputing the window — **avoided**: the predicate filters days, and the upstream staging views carry every `batch_id <= d6_batch`, so 2026-07-01 CT-A was rebuilt from all four of its deliveries rather than topped up from D016 alone. (3) the fan-out, header amounts summed over line-grain rows (SILENT, survives all eight verification items) — **avoided, sixth setup of the escalated blindspot and the second one avoided**: `int_d6_not_cancelled_latest` collapses adjustments to `delivery_id` before the left join, so `payout_base_usd` is summed once per delivery and every cell of all four snapshots is exact. Absent from the verdict — the counter-measure was written without being named. (4) `CASE WHEN` where the spec needs `WHERE`, both halves — **avoided**: `where status <> 'CANCELLED'` runs in the intermediate model before the adjustment join, so (2026-07-03, CT-B) produces no row and A004's 1.00, owned by cancelled D003, never reaches (2026-07-01, CT-A). (5) NULL watermark on an empty target — **avoided**: `coalesce(max(delivery_date), cast('1900-01-01' as date))` is present, not merely unreached. (6) type drift — **avoided**: all seven mart columns match the contract, `INTEGER` ×2 and `DECIMAL(10,2)` ×3, identical to the reference. **All six traps avoided in code; all four snapshots match Expected Output cell for cell, including the run-3 reach-back and the full-refresh equivalence.** The day was nonetheless not a pass, and every point lost was in the verification layer he wrote himself: `models/day6/staging/schema.yml` declared the model as `stg_d6_delivery`, one character short of `stg_d6_deliveries`, so dbt emitted `Did not find matching node for patch` as a **WARNING** and silently dropped all eight V1 tests — including the `unique` on `delivery_id` that the day was built to make him reason about — while `dbt build` still reported `WARN=0`; V7's reconciliation used `cnt_stg left join fct ... where stg_cnt <> delivery_count`, and a missing mart row yields `delivery_count IS NULL`, so `stg_cnt <> NULL` evaluates to NULL and is discarded by the `where` — the missing-pair direction, which is this day's designed failure mode and the reason V7 exists, cannot fire; V8 joined `agg_raw ar, fct` with no predicate, a cartesian product that failed every build with exactly n²−n rows (2 / 42 / 90 against marts of 2 / 7 / 10). Node counts: reference 39, his 23. Reference `PASS=39 WARN=0 ERROR=0 SKIP=0` on all four builds, every cell and every type exact.

- Key takeaways:
  - `schema.yml` 里的 model name 是**按名字绑定**的，绑不上时 dbt 发的是 **WARNING 不是 ERROR** —— `Did not find matching node for patch with name 'x'`，然后那个 model 下面挂的所有 generic test 会因为依赖一个不存在的节点而被静默丢弃，`dbt build` 照样 `WARN=0 ERROR=0` 全绿。**「测试没注册」和「测试跑了且通过」在 `Done. PASS=…` 这一行里是同一个样子**，差别只在总数上。所以绿灯不是证据，**节点数才是**：`dbt ls --resource-type test --select path:models/dayNN | wc -l` 数一遍，或者把 `dbt parse` 的 warning 当错误读（本次它连喊了 9 遍）。这一天 23 vs 39 的差距就是这么来的，而且丢掉的恰好是题目专门设计来考「write-once feed 该不该加 unique」的那 8 个。
  - 对账测试（reconciliation）必须用 **`full outer join`**，`left join` 只能覆盖一个方向，而且是**不重要**的那个方向。机制在 NULL 的三值逻辑：mart 缺整行时 join 出来的 `delivery_count` 是 NULL，`stg_cnt <> NULL` 求值为 **NULL 而不是 TRUE**，`where` 只保留 TRUE，于是那一行被丢掉 —— 一个「mart 从来没写过的行」对任何从 mart 出发、或用 `<>` 比较的测试都是**不可见**的，而那正是增量模型最典型的坏法（漏算一天）。再加一条 `mart_row_count <> 1`，「恰好一行」才和「唯一性」解耦。顺带：`from a, b where …` 少写 join 条件不会报错，只会变成笛卡尔积，失败行数是 **n²−n** —— 看到 2 / 42 / 90 对应 2 / 7 / 10 行的表，不用查就知道是缺了 join 谓词。
  - 增量回看窗口（lookback window）的宽度**从 SLA 推导，不是拍的**：「最晚迟到 4 个日历日」+「delivery_date 不会晚于自己的 load date」⇒ 任何新到行都满足 `delivery_date >= L-4`，而 mart 的 `max(delivery_date) <= L`，所以 `max - 4` 一定在安全线之下。推完之后 **`>` 和 `>=` 就不是风格问题**：SLA 给的是闭区间，写 `>` 等于把窗口从 4 天缩成 3 天，恰好丢掉边界那一天。本次数据里 2/3/4 天宽都能算对，所以**测试全绿、逐格比对也全对，错误依然存在** —— 这类「数据惩罚不到的规格违反」只能靠读代码抓，不能靠跑。窗口选的是**「哪几天要重算」而不是「哪些行是新的」**，选中之后那几天要用全量上游重算，再用 `delete+insert` 整段替换。
