## Trap 1 — no lookback window (HEADLINE; surfaces as a FAILING TEST via V7)

**Naive code**

```sql
{% if is_incremental() %}
where delivery_date >= (select max(delivery_date) from {{ this }})
{% endif %}
```

**What happens.** Runs 1 and 2 are *correct* under this filter, which is the point — it
looks like a working incremental model for two nights.

- After run 1 the mart's `max(delivery_date)` is `2026-07-01`. Run 2's filter is
  `>= 2026-07-01`, which happens to cover the entire dataset, so run 2 matches the
  7-row snapshot exactly.
- After run 2 the watermark is `2026-07-03`. Run 3's filter is `>= 2026-07-03`, so only
  2026-07-03 and 2026-07-04 are recomputed. Batch 3's two 4-day-late rows — **D015**
  (CT-C, 2026-07-01, 13.00) and **D016** (CT-A, 2026-07-01, 6.50) — are never seen.

**Resulting mart after run 3: 9 rows instead of 10.**

- `(2026-07-01, CT-A)` stays at run 2's `3 | 3 | 26.00 | 8.25 | 34.25`; correct is
  `4 | 4 | 32.50 | 10.25 | 42.75`.
- `(2026-07-01, CT-C)` — `1 | 1 | 13.00 | 3.75 | 16.75` — is missing entirely.

**Which tests fire.** V7 (reconciliation) FAILS on both directions: the count mismatch
on `(07-01, CT-A)` and the pair `(07-01, CT-C)` present in staging and absent from the
mart. **V1, V2, V3, V4, V5, V6 and V8 all stay green** — every row that *is* there is
internally consistent. This is the mandatory failing-test trap.

**Also caught by:** the `--full-refresh` equivalence check (10 rows vs 9).

**Correct shape.** Subtract the SLA from the watermark:

```sql
{% if is_incremental() %}
where delivery_date >= (
    select coalesce(max(delivery_date), date '1900-01-01') - interval 4 day
    from {{ this }}
)
{% endif %}
```

Discrimination on this data: a width of **0 or 1 days fails**; 2, 3 and 4 all produce the
correct table. 4 is the only width derivable from the stated SLA, so widths of 2 and 3
are a code-reading call, not a data call — score them as spec violations that this
dataset does not punish, and say so.

## Trap 2 — recomputing from the new batch instead of recomputing the window

**Naive code.** Any of: filtering staging by `batch_id = {{ var('d6_batch') }}` instead
of `<=`; adding `where loaded_at > (select max(loaded_at) from {{ this }})`; selecting
only batch-3 rows into the mart's incremental branch.

**What happens.** The incremental filter's job is to select **which days to recompute**,
not **which rows are new**. Under a row-level filter, run 3 rebuilds `(07-01, CT-A)` from
D016 alone — `1 | 1 | 6.50 | 2.00 | 8.50` — and `delete+insert` on the grain key wipes the
correct 3-delivery row and replaces it with that fragment. Every day the batch touches
loses its history.

**Which tests fire.** V7 FAILS (staging says 4 deliveries, mart says 1). V3/V4/V5/V6/V8
stay green. Also caught by the equivalence check.

**Note for review.** This is a *different defect from trap 1* even though V7 catches both.
Distinguish them by the shape of the wrong row: trap 1 leaves a **stale** row, trap 2
leaves a **truncated** one, and trap 1 also leaves `(07-01, CT-C)` missing while trap 2
creates it.

## Trap 3 — the fan-out (SILENT; survives all eight verification items)

**Sixth setup of the escalated blindspot** `[modeling] counting at a grain that is not
the entity being counted`. Day 5 was the first one avoided, and the digest recorded that
pass as *fragile*: the `## Grain plan` still put a header amount at the mart's grain.
This day re-runs it with the written plan explicitly targeted (`## Grain plan` now says
"write the grain it is *computed at*, not the grain it is *published at*").

**Naive code**

```sql
from stg_d6_deliveries d
left join stg_d6_delivery_adjustments a on a.delivery_id = d.delivery_id
...
group by d.delivery_date, d.city_code
```

then `sum(d.payout_base_usd)`.

**What happens.** Deliveries with more than one adjustment line are counted once per
line. Multi-line deliveries: D001 (2), D005 (3), D007 (2), D010 (2), D015 (3).
Run 3, `(2026-07-01, CT-A)`: `8.00 * 2 + 9.50 + 8.50 + 6.50 = 40.50` against a correct
`32.50`. `(2026-07-01, CT-B)`: `6.25 + 7.75 * 3 = 29.50` against `14.00`.
`(2026-07-01, CT-C)`: `13.00 * 3 = 39.00` against `13.00`. `total_payout_usd` inherits
every one of those errors.

**Which tests fire.** With `count(*)`, V7 fires on the counts and the fan-out is loud.
With `count(distinct delivery_id)` — the rescue a solver reaches for the moment V7 goes
red — **V7 goes green and the money stays wrong**. V8 also stays green, because
`total_payout_usd` is computed from the two inflated columns and is internally consistent
with them. **Nothing in V1–V8 catches the inflated `payout_base_usd`.** Only the cell
comparison does.

This is the day's only fully silent trap and the subject of debrief question 4.

**Correct shape.** Aggregate adjustments to `delivery_id` first, then left join
one-to-one against the delivery header.

## Trap 4 — `CASE WHEN` where the spec needs `WHERE` (two-part, one loud one silent)

Repeat of Day 5 trap 5, kept because the cancelled delivery this time **owns an
adjustment line** (A004, D003, TIP 1.00).

- **Loud part.** Filtering cancellations with `sum(case when status <> 'CANCELLED' …)`
  instead of a `WHERE` leaves `(2026-07-03, CT-B)` in the mart as a row of zeros from
  run 2 onward (D012 is the only delivery in that pair and it is cancelled). **V5 FIRES**
  — `delivery_count >= 1` is violated. The expected output has no such row.
- **Silent part.** If the cancel filter is applied to the *delivery header* but the
  adjustment lines are joined without inheriting it, A004's `1.00` leaks into
  `(2026-07-01, CT-A)`: `adjustment_total_usd` becomes `7.50 / 9.25 / 11.25` at runs
  1 / 2 / 3 instead of `6.50 / 8.25 / 10.25`, and `total_payout_usd` follows. **No test
  catches this** — V8 stays green because the sum is still internally consistent.

## Trap 5 — NULL watermark on an empty target (MINOR, self-announcing)

`max(delivery_date) from {{ this }}` returns `NULL` against an empty table, and
`delivery_date >= NULL` evaluates to NULL, not TRUE — a silently empty mart.
`is_incremental()` guarantees the relation **exists**, not that it has rows.

Mostly defused this day because run 1 uses `--full-refresh`, so the guard is skipped on
the only run where the table could be empty. Score it as present/absent in the code, not
by whether it fired. It is a repeat of a Day 5 key takeaway, so absence is a regression,
not a new gap.

## Trap 6 — type drift (MINOR, recurring since Day 4)

`count(*)` and `count(distinct …)` return `BIGINT` in DuckDB; the contract says
`integer`. `sum()` over `decimal(10,2)` returns `DECIMAL(38,2)`; the contract says
`decimal(10,2)` for `payout_base_usd`, `adjustment_total_usd` and `total_payout_usd`.
Seven columns, four of them needing an explicit cast. Day 5 landed two `BIGINT`s against
an `integer` contract and only fixed them in the post-review pass. `## Pass condition`
says "including column types" four times.

## What the day is really testing

1. That the incremental predicate is a **day selector**, not a row filter (traps 1, 2).
2. That "all tests green" is not evidence about an incremental model — seven of eight
   items stay green under trap 1, and all eight stay green under trap 3 (traps 1, 3).
3. That the header/line grain is settled **before** the `from` clause, not after
   (trap 3, and the `## Grain plan` deliverable).
4. That a stated contract is read case by case: V1 asks for a `unique` on the header
   business key where Day 5 explicitly forbade it, and the reason is stated in
   `### The feeds` (write-once vs state log). Day 5's blindspot log has
   `[general] substituting a blanket rule for case-by-case reasoning` at three
   occurrences; this is the fourth setup.
