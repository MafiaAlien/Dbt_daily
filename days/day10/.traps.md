## T1 — the `other` bucket built with `not in` is NULL-blind  (failing test: V6)

**Setup.** P06 (O03 → M1 2026-09, 12.00) and P18 (O11 → M3 2026-10, 18.00) are captured
payments with no `payment_method`. Staging is told to keep the missing value. The definition of
`other_*` is "method is not one of the methods in the list", and a missing method is not one of
them, so both belong in `other`.

**Naive.** The loop naturally emits the complement as
`case when payment_method not in ('card', 'wallet', 'bank_transfer') then …`, built with
`{% for %}` plus `loop.last` to place the commas. That is exactly the shape this day teaches,
and `NULL not in (…)` is NULL, so the `case` falls to its `else`. Result, run 1:
- M1 2026-09: `other_order_count` 0 (expected 1), `other_amount_usd` 0.00 (expected 12.00)
- M3 2026-10: `other_order_count` 0 (expected 1), `other_amount_usd` 0.00 (expected 18.00)
Run 2 shows the same two cells.

**Caught by.** V6: `sum(method amounts) + other_amount_usd = captured_amount_usd`. It fails on
M1 2026-09 (175.50 vs 187.50) and on M3 2026-10 (200.00 vs 218.00), giving `FAIL 2` on both
runs. `captured_amount_usd` is computed independently of the method filter, so it ties to staging
and V8 stays green.

**Correct shapes.** `payment_method is null or payment_method not in (…)`;
`coalesce(payment_method, '') not in (…)`; or invert it as
`case when payment_method in (…) then 0 else amount_usd end`, where the `else` captures NULL.

**Interaction with T2. Record this in the review.** If T2 is also hit, the per-method amount
columns carry NULLs. Then V6's left side is NULL on M1 2026-09 (`bank_transfer_amount_usd`
NULL) and on M3 2026-10 (`card_amount_usd` NULL), `NULL <> 187.50` is NULL, and V6 cannot fire
on exactly the two rows T1 corrupts. **T2 masks T1.** T1 surfaces only once T2 is fixed.
Separately, a V6 written as `where lhs <> rhs` with no NULL guard is Day 6's V7 shape (the
`x <> NULL` blindspot). A correct V6 uses `is distinct from` or coalesces every term.

**Secondary (silent).** Without `lower()` in staging, P05 `Wallet` lands in `other`: M1
2026-09 shows wallet 1 / 80.00 and other 1 / 42.00, where the expected values are wallet 2 /
110.00 and other 1 / 12.00. In run 2, P14 `BNPL` lands in `other` as well. V6 still balances,
so only the Expected Output comparison catches it. P03 `CARD` is failed and changes nothing.

## T2 — an absent method yields NULL, not 0.00  (failing test: V5; secondary V4)

**Setup.** Every row has at least one method with no captured payment: M1 2026-09 has no
bank_transfer, M2 2026-09 has no card or wallet, and M3 2026-09 (O13, only a failed payment)
has nothing at all. The contract says `0.00 when there are none`.

**Naive.** `sum(case when payment_method = '{{ m }}' then amount_usd end)`, with no `else` and
no `coalesce`, returns NULL for every (row, method) pair without a match. The counts are safe:
`count(distinct case … end)` returns 0 on no match, so the trap is on the amount columns only.
A further shape: the mart is built as `orders left join int`, and M3 2026-09 has a single
null-padded row, so `captured_amount_usd` is `sum(NULL)` = NULL unless coalesced. V4's
`not_null` catches that.

**Caught by.** V5, the loop over the var plus `other`, `is null or < 0`. Run 1 has NULL
amount cells on all 6 rows (a per-row test gives `FAIL 6`). Run 2 adds bnpl NULLs on four rows
and still fails all six. V4 catches `captured_amount_usd` on M3 2026-09 (`FAIL 1`) if it is not
coalesced.

**Correct shapes.** `sum(case when … then amount_usd else 0 end)`, or
`coalesce(sum(case …), 0)`, then cast to `decimal(12,2)`. Note that with `else 0` the null-padded
row of a left join also yields 0 for every method column, because `NULL = 'card'` → else → 0.

## T3 — the counted entity is the order, not the payment  (failing test: V8, for (a) and (b); (c) silent)

Three shapes of the `[modeling] counting at a grain that is not the entity being counted`
blindspot (setups 1–9, avoided on Days 5–9 in code, never articulated in `## Plan`). `## Plan`
part 1 asks for the rows-per-order answer for a fifth time.

**(a) Fan-out on `order_count`.** `stg_d10_orders left join int_d10_captured_payments` then
`count(*)`, or `count(order_id)` without `distinct`. Rows per order: O01 2, O02 1, O03 2, O04 1,
O05 0→1, O06 2, O07 1, O08 2, O09 2, O10 1, O11 2, O12 0→1, O13 0→1. That gives M1 2026-09 5
(expected 3), M1 2026-10 3 (2), M2 2026-10 5 (3), M3 2026-10 3 (2), with M2 2026-09 2 and M3
2026-09 1 unchanged. **V8: `sum(order_count)` 19 vs 13 → FAIL.** Pre-aggregating payments to
`order_id` before the join, or using `count(distinct order_id)`, avoids it.

**(b) Losing orders with no captured money.** The mart is built from the int alone, or from
`orders left join stg_d10_payments … where status = 'captured'`, which turns the left join into
an inner join. O05 (only P08, failed), O12 (no payments) and O13 (only P20, failed) drop out.
M2 2026-09 `order_count` becomes 1 (expected 2), M3 2026-10 becomes 1 (expected 2), and **the
M3 2026-09 row disappears**, leaving 5 rows. **V8: 10 vs 13 → FAIL.** The status filter must
live in the int (as specified) or in the join condition, never in a `where` on the outer side.

**(c) Per-method counts of payments instead of orders.**
`sum(case when payment_method = '{{ m }}' then 1 else 0 end)` or
`count(case when … then 1 end)`. Run 1: M1 2026-09 `card_order_count` 2 (expected 1; P01 and P02
split on O01), M2 2026-10 `other_order_count` 3 (expected 2; P12, P14, P15). Run 2: M2 2026-10
`bnpl_order_count` 2 (expected 1; P14 and P15 are instalments on O09). **No test catches it.**
V5 checks `>= 0`, V6 checks amounts, and V8 checks `order_count` only. Only the Expected Output
comparison catches it, which re-exercises
`[dbt] reviewing one's own solution without comparing outputs` (ninth occurrence on Day 9).
Correct shape: `count(distinct case when … then order_id end)`.

Related: if failed payments leak into per-method counts (status not filtered before the pivot),
M1 2026-09 card becomes 2 (P03 `CARD` on O02, if lower-cased), M2 2026-09 card 1 (P08), and M3
2026-09 wallet 1 (P20). The int's spec prevents this if it is followed.

## Not traps, but graded (blindspot re-exercise)

- **Types** (`[dbt] aggregate types not cast back to the contract`, held on aggregates on Day 9
  and widened to a VARCHAR date the same day). `order_month` via bare `date_trunc` is
  **TIMESTAMP**, not DATE. Day 9's derived-column shape again, from the other direction. Counts
  are BIGINT and amounts DECIMAL(38,2) unless cast. In a loop the cast must be inside the loop
  body, and the capture header shows each type.
- **One place.** A hard-coded `{% set methods = [...] %}` in the model, or a list copied into
  V5 / V6, means run 2 produces no `bnpl_*` columns (model) or does not cover them (test). The
  grep check catches the quoted literals. A `{% set %}` written with double quotes would slip
  past the grep, but run 2's 14-column Expected Output still catches it in the model; in a test
  only the compiled test SQL would show it.
- **`var()` with a default argument** (`var('d10_payment_methods', [...])`) is a second copy of
  the list, though harmless while the project var exists. If it appears, ask in the review why.
- **Whitespace / trailing comma.** A comma after the last generated column before `from` is a
  Parser Error, not a test failure: environment-shaped, but it is his. Run 1 would show it.
- **V8 reads staging.** Expected answer in `notes.md`: the int already carries the captured
  filter and the merchant-month attribution, so a tie-out against the int would share any bug
  in them. Day 9's V12 rule.

## Debrief — what a full answer contains

1. Var: deterministic schema, columns change only by a reviewed decision, and a new method
   lands in `other` safely (totals still balance). Data-driven (`get_column_values`): the schema
   drifts on its own the night a new value appears; a downstream `select card_amount_usd` keeps
   working, but a new column appears unannounced and a typo'd source value becomes a column. It
   also needs a database query at compile time. Reverse it when the consumer is exploratory or
   the list is large or volatile, and no downstream contract depends on the column names.
2. Incremental with the default `on_schema_change: ignore`: the new `bnpl_*` columns are not
   added to the target. The insert uses the target's columns, so bnpl values are dropped, and
   rows that were not reprocessed keep `other_amount_usd` including bnpl (M1 2026-10 120.00, M2
   2026-10 115.00). `append_new_columns` / `sync_all_columns` add the columns but **do not
   backfill** old rows: the existing rows have NULL bnpl and stale `other`. Only
   `--full-refresh` restates history.
3. Rendering happens at compile time, per node. DuckDB receives plain SQL with no Jinja (the
   compiled file). `var()` comes from project config / CLI and is available at parse.
   `run_query` needs a live connection, which does not exist during parse (`execute` is False),
   so it must be guarded or the parse-time render fails or returns None. Day 5's takeaway on
   `is_incremental()` / `execute` applies directly.
4. Long form: adding a method needs no schema change, it is easy to filter and aggregate, and it
   is BI-friendly for pivot tables. But "one row per merchant-month" is gone, absent methods
   have no row (zero rows vs a 0 value), and per-row identities like V6 need a group-by. Wide:
   column-addressable and dashboard-ready, but every new method is a schema change, and
   consumers that `select *` or bind by position break or silently gain columns. Whoever owns
   the downstream dashboard notices first under wide; under long, nobody notices, and that is
   the risk (a new method just appears as a new slice).
