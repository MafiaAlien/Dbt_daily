- Problem: a marketplace's captured payments pivoted into one row per (`merchant_id`, `order_month`) with an order-count / amount pair per payment method, every method-dependent column generated by a Jinja loop over the project var `d10_payment_methods` and no method name typed into any `.sql` file; run 2 adds `bnpl` on the command line, and the mart (12 → 14 columns) and its loop-generated tests V5 / V6 must follow with no file edited; no packages, four singular intent tests, a red proof for three of them.

- Key takeaways:
  - Pivot mart 的 grain 由 **spine** 决定，不由事实表决定：先从 `stg_d10_orders` 建 merchant-month spine（`order_count` 在 order 粒度上 `count(*)`），再 left join 已按 merchant-month 预聚合好的 payment metrics，最后 `coalesce(..., 0)`。直接从 int（captured payment 粒度）出发，会同时犯 Day 1 和 Day 3 的两种错：fan-out（`count(*)` 数的是 payment，M1/09 是 5 而不是 3），以及丢失（没有 captured payment 的 order 和 merchant-month 消失，M3/09 整行没了）。per-method 计数要写 `count(distinct case when payment_method = 'm' then order_id end)`；`count(case … then 1 end)` 数的是 payment，split tender 和 instalments 会把一个 order 数两次。这种错误**没有任何 test 能抓**（V5 只看 `>= 0`，V6 只看金额），只能靠逐格比对 Expected Output。
  - `var()` 和 `{% for %}` 在 **compile 时**按 node 展开，DuckDB 收到的是 `target/compiled/` 里的纯 SQL，所以要 review 的是编译后的 SQL，而不是 Jinja 模板。循环生成的每一列都要在 loop 体内各自 `cast` 回 contract 类型：DuckDB 的 `count()` 返回 BIGINT；`date_trunc('month', TIMESTAMP)` 返回 TIMESTAMP 而不是 DATE（`dbt.date_trunc` 只做 cross-database 转发，不改返回类型），所以要 `cast(... as date)`。`other` 桶要写成 `payment_method is null or payment_method not in (...)`，因为 `NULL not in (...)` 求值为 NULL，没有 method 的 payment 会掉出所有桶。
  - Intent test 要逐字对照 spec 写，并在已知输入上看它红一次、绿一次。V6 规定比较的是**本行**的 `captured_amount_usd`，拿去和 int 的 sum 比就成了另一个断言，`captured_amount_usd` 本身算错它看不见。V5 用 `and` 连接 count 条件和 amount 条件，只有两者同时坏才会红。V8 是唯一能抓 T3 的 test（`sum(order_count)` 16 vs 13），却因为 `ref()` 名字写错被 dbt 静默禁用：parse WARNING 不计入 `Done.` 行的 `WARN=`，"没运行的 test" 和 "通过的 test" 在 `PASS=28` 里看起来一模一样，只有 `dbt ls` 的计数（24 vs 25）能区分。

- Parking lot additions: var-driven vs data-driven pivot column lists (debrief Q1, unanswered) — a project var gives a deterministic schema that changes only by a reviewed decision, and a new method lands safely in `other` with totals still balancing, while `run_query` / `get_column_values` drifts the schema on its own the night a new value appears (a typo'd source value becomes a column) and needs a database query at compile time; reverse it for exploratory consumers with no downstream contract on column names. A pivot mart under incremental `on_schema_change` (debrief Q2, unanswered) — under the default `ignore`, the new `bnpl_*` columns are never added and old rows keep bnpl inside `other_amount_usd`; `append_new_columns` / `sync_all_columns` add the columns but do not backfill, so only `--full-refresh` restates history. Compile-time rendering and the `execute` guard (debrief Q3, unanswered) — `var()` and `{% for %}` resolve at compile time from project config and the CLI, and DuckDB receives plain SQL, while `run_query` needs a live connection that does not exist during parse (`execute` is False), so it must be guarded and a var need not be. Long vs wide pivot shape (debrief Q4, unanswered) — the long form needs no schema change when a method is added and is easy to filter, but loses one row per merchant-month and turns a 0 into a missing row; the wide form is dashboard-ready, but every new method is a schema change, so under wide the dashboard owner notices first, and under long nobody notices.
