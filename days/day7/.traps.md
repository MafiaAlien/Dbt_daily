# Day 7 — trap notes

**Do not read outside `/review 7` phase 3 (after phases 1 and 2 have run in that same
conversation) or `/digest 7`.**

Topic: snapshots, timestamp strategy, `dbt_valid_from` / `dbt_valid_to`, point-in-time
attribution. Four traps. T1 surfaces as a failing generic test; T2 and T4 surface through
the reconciliation test V9 if it is written in both directions; **T3 passes all eleven
verification items and is visible only by comparing cells.**

---

## T1 — the interior boundary: `between` double-matches

**The naive move.** `on o.order_ts between s.dbt_valid_from and s.dbt_valid_to`, usually
with `coalesce(s.dbt_valid_to, timestamp '9999-12-31')` bolted on once the open end is
noticed. `between` is inclusive on both ends, so an order whose `order_ts` falls exactly
on an interior boundary matches **two** versions: the one that ends at that instant and
the one that begins at it.

**The data.** Two orders sit on interior boundaries:

- `O-002`, A100, `2026-03-12 09:30:00` — A100's STANDARD→PREMIUM boundary.
- `O-013`, A200, `2026-03-22 11:00:00` — A200's STANDARD→ENTERPRISE boundary.

`O-011` (A400, `2026-03-14 10:00:00`) also sits exactly on a `dbt_valid_from`, but it is
A400's **first** version, so there is no earlier window to double-match. It is there to
make the boundary decision matter on a row where only one operator can be wrong:
`>` instead of `>=` turns `O-011` from `STANDARD`/`APAC` into `UNKNOWN`/`UNKNOWN`, and
nothing else in the data moves.

**Measured, against the run-3 snapshot (13 orders, correct total 15806.50):**

| predicate | fact rows | duplicated | `sum(order_amount_usd)` |
|---|---|---|---|
| `>= from and (to is null or < to)` — correct | 13 | — | 15806.50 |
| `between from and coalesce(to, '9999-12-31')` | 15 | `O-002`, `O-013` | 18857.00 |
| `between from and to` (open end left raw) | 14 | `O-002` | 16607.00 |
| `> from and (to is null or <= to)` — flipped, not inclusive | 13 | — | 15806.50 |

The last row is the `O-011` case: row count and total stay right, and one cell —
`O-011`'s `tier_at_order` / `region_at_order` — silently becomes `UNKNOWN` / `UNKNOWN`.
No test fires on it except **V10**.

**What catches it.** V8's `unique` on `order_id` — **red**. Also V9 in either direction
(count mismatch, amount mismatch). This is the day's failing-test trap and it is loud.

**Why it is the Day-1/3/4 fan-out blindspot in a new costume.** It is an interval join,
not an equijoin, so the "aggregate the many side first" reflex from Days 4-6 does not
fire. The count that goes wrong is 1 → 2 on a single row, and the money follows it.
Blindspot log entry `[modeling] Counting at a grain that is not the entity being counted`
— this would be the seventh occurrence and the first in interval form.

## T2 — the open end: `dbt_valid_to is null` is not a date

**The naive move.** `between dbt_valid_from and dbt_valid_to` with nothing done about the
`NULL`. `x between a and NULL` is `NULL`, never `TRUE`, so **every order that falls in a
current (open) window silently fails to match.**

**The data.** Against the run-3 snapshot, five orders fall in a current (open) window:
`O-004`, `O-007`, `O-009`, `O-012` and `O-013`. Under `between from and to` with the
`NULL` untouched, four of them match nothing at all — `O-013` is the exception, because
it sits exactly on A200's interior boundary and so matches the *closed* window instead,
picking up `STANDARD` where the answer is `ENTERPRISE`. Measured: **14 rows, sum
16607.00, `O-002` duplicated, `tier_at_order` unmatched on `O-004`, `O-007`, `O-009`,
`O-010`, `O-012`.**

**What catches it.**

- With `LEFT JOIN` and no `coalesce`: V8's `not_null` on `tier_at_order` — **red**.
- With `LEFT JOIN` and a `coalesce(…, 'UNKNOWN')`: in its **isolated** form — the
  boundary handled correctly but the open end not, i.e.
  `order_ts >= dbt_valid_from and order_ts < dbt_valid_to` — there is no duplication, so
  every test stays **green** except **V10**. Four orders (`O-004`, `O-007`, `O-009`,
  `O-012`) read `UNKNOWN` while a version covers them. V10 exists for exactly this. If
  V10 is written weakly or skipped, this becomes a second silent trap: four wrong rows,
  eight wrong cells, all tests green.
- With `INNER JOIN`: V9 in the staging→mart direction — **red** — but **only if** V9 is
  written both ways. `stg left join mart … where mart.x <> stg.x` cannot fire on a
  missing mart row. That is verbatim Day 6's V7 defect, which is why `## Verification`
  names it in the brief this time.

## T3 — attributing by the current tier — SILENT, survives everything

**This is the trap of the day.** The seductive shortcut is one join to
`dim_d7_accounts_current` (or to `snap_d7_accounts where dbt_valid_to is null`), used for
**both** `tier_at_order` and `current_tier`. It yields exactly one row per order, no
fan-out, no `NULL`s, and **all eleven verification items pass**: V8's `unique` and
`not_null` are satisfied, V9 reconciles row-for-row and cent-for-cent, V10 sees no
illegal `UNKNOWN` except the A300 rows, and V11 is satisfied by construction.

**What it costs.** Eight of thirteen rows carry a wrong `tier_at_order`:

| order | correct `tier_at_order` | under T3 | correct `region_at_order` | under T3 |
|---|---|---|---|---|
| `O-001` | STANDARD | PREMIUM | EMEA | UK |
| `O-003` | STANDARD | PREMIUM | EMEA | UK |
| `O-005` | STANDARD | ENTERPRISE | AMER | AMER |
| `O-006` | STANDARD | ENTERPRISE | AMER | AMER |
| `O-008` | PREMIUM | UNKNOWN | AMER | UNKNOWN |
| `O-009` | PREMIUM | UNKNOWN | AMER | UNKNOWN |
| `O-010` | UNKNOWN | PREMIUM | UNKNOWN | APAC |
| `O-011` | STANDARD | PREMIUM | APAC | APAC |

`O-002` is a ninth row where only the *region* is wrong — `EMEA` correct, `UK` under T3 —
because A100's tier change and its region change are separate versions. `O-010` moves the
wrong way: it is the one row where the shortcut invents an answer where the correct one
is `UNKNOWN`.

Revenue by `tier_at_order`, correct versus T3 — both total 15806.50, so no
reconciliation test can see the difference:

| tier | correct rows | correct revenue | T3 rows | T3 revenue |
|---|---|---|---|---|
| STANDARD | 5 | 4551.00 | 0 | 0.00 |
| PREMIUM | 5 | 5430.50 | 7 | 6956.25 |
| ENTERPRISE | 2 | 5550.00 | 4 | 7750.25 |
| UNKNOWN | 1 | 275.00 | 2 | 1100.00 |

**STANDARD revenue disappears entirely** — 4551.00 of 15806.50, 28.8% of the book,
reassigned to the tiers those accounts have since upgraded to. Not one test goes red.
This is also the answer to debrief question 4's "how much revenue moves".

**Detection in `/review`.** Cell comparison only. The tell in the code is a single join
to the current dim, or a `where dbt_valid_to is null` filter reached before `order_ts` is
mentioned. The tell in the output is `tier_at_order` equal to `current_tier` on all
thirteen rows — `## Expected Output` says in the prose that eight must differ.

**Blindspot connection.** `[dbt] Reviewing one's own solution only against the
reference's style, never comparing outputs` — six occurrences. This trap cannot be caught
any other way, which is why it was chosen.

## T4 — the first `dbt_valid_from` is not the beginning of time

**The naive move.** Assume every order falls inside some window, and use an `INNER JOIN`.
Under the timestamp strategy the first version's `dbt_valid_from` is its own
`updated_at`, not `-infinity`, so an order placed before an account's first version
matches nothing.

**The data.** `O-010` — A400, `2026-03-10 14:20:00`, 275.00. A400's first version arrives
in batch 2 with `updated_at = 2026-03-14 10:00:00`. Correct output is `UNKNOWN` /
`UNKNOWN`, with the row present.

Measured: `INNER JOIN` with the correct predicate yields **12** rows instead of 13, and
`sum(order_amount_usd)` 15531.50 instead of 15806.50.

**What catches it.** V9, staging→mart direction only, and only if written so a missing
row fires. V8's `unique` stays green (12 distinct ids are still unique). V10 stays green
(no illegal `UNKNOWN`, because the row is absent rather than `UNKNOWN`). If V9 is
one-directional this is the **second** silent trap of the day.

## Secondary things worth grading, not traps

- **Dedup placement.** `int_d7_account_feed_latest` must yield one row per `account_id`.
  Feeding the snapshot a multi-row-per-key relation corrupts the history rather than
  erroring loudly. V3 (`unique` on `account_id`) is the guard. If he skips the
  intermediate and deduplicates inside the snapshot's relation some other way, that is
  acceptable — grade the grain, not the file count.
- **The lost version.** A200 `PREMIUM` at `2026-03-15 08:00:00` lands in batch 3 together
  with `ENTERPRISE` at `2026-03-22 11:00:00`. Only the latter is ever snapshotted, so the
  PREMIUM window never exists and `O-006` (`2026-03-18 09:00`) is attributed `STANDARD`.
  This is **correct output** for this pipeline and the subject of debrief question 2. It
  is not a defect; do not grade it as one. Do grade whether he found it — the problem
  says nine rows for ten versions and asks him to name the missing one.
- **Churn handling.** A300's current version is `CHURNED`, so it is absent from
  `dim_d7_accounts_current` (3 rows, not 4) and `current_tier` is `UNKNOWN` on `O-008`
  and `O-009` — while `tier_at_order` is `PREMIUM` on both, because the history keeps the
  churned account. Filtering `ACTIVE` in the **snapshot relation** instead of downstream
  would be a real defect: with `hard_deletes` at its default the account would silently
  stop being tracked. The problem forbids it implicitly ("no filtering … beyond the
  `batch_id` clause"); check whether he can say *why*.
- **Test binding.** Expected assertion count for V1-V11 is **39**:
  V1 8, V2 5, V3 2, V4 4, V5 1, V6 1, V7 6, V8 9, V9 1, V10 1, V11 1.
  `dbt ls --resource-type test --select path:models/day7 path:snapshots/day7
  path:tests/day7 --quiet | wc -l` should print 39. A lower number means a patch did not
  bind — Day 6's failure, now instructed against in the brief.
- **Snapshot form.** YAML `snapshots:` block is required by the problem. The legacy
  `{% snapshot %}` SQL block still parses in dbt 1.12 without a deprecation warning, so
  if he uses it the build stays green; grade it against the brief, not against the
  compiler.
- **`--full-refresh`.** The problem forbids it. If the run log shows one, the snapshot
  was dropped and rebuilt from whatever batch was current, and every earlier window is
  gone — check the captured tables against the run they claim to be.
