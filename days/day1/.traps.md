## Trap 1 — `sum()` over an all-NULL group returns NULL, not 0

**Mechanism.** `total_amount` is defined as never null, zero when nothing was captured.
Customer 3 (Carol Ng) has exactly one order, and its `Amount` is empty. Customer 4
(Dan Wu) has no orders at all.

**Naive solution.** `sum(o.amount)` with no `coalesce`. SQL `sum()` skips NULLs, and over
a group where every value is NULL — or over a LEFT JOIN row that matched nothing — it
returns NULL rather than 0.

**Result.** `fct_d1_customer_orders` gets `total_amount = NULL` for customer_id 3 and 4.

**Caught by.** `not_null` on `fct_d1_customer_orders.total_amount` → **FAILING TEST**
(2 failing records). This is the trap that satisfies the "at least one trap must surface
as a failing test" rule.

**Correct.** `coalesce(sum(o.amount), 0)` or `sum(coalesce(o.amount, 0))`. Both give
0.00 here; they diverge only if the requirement had been "null when the customer has
never ordered", which it is not.

## Trap 2 — driving the mart from orders instead of from customers

**Mechanism.** The stated grain is "one row per customer in `stg_d1_customers`",
including customers who have never ordered. Aggregating `stg_d1_orders` and grouping by
`customer_id` is the reflex, and it is wrong in two directions at once.

**Naive solution.**

```sql
select customer_id, count(*) as order_count, sum(amount) as total_amount
from {{ ref('stg_d1_orders') }}
group by customer_id
```

**Result.**
- Customer 4 (Dan Wu, zero orders) is **missing** — 3 rows instead of 4, and
  `customer_name` cannot be produced at all without joining customers anyway.
- Orders 1006 and 1007 are guest checkouts with an empty `CustomerID`. They collapse
  into a single group with `customer_id = NULL`, adding a phantom row worth 37.50.

**Caught by.** `not_null` on `fct_d1_customer_orders.customer_id` → **FAILING TEST**
(1 failing record, the guest group). The missing Dan Wu row is caught by the Expected
Output comparison, not by a test — `unique` and `relationships` both pass on a mart that
is simply short one customer. Worth pointing out in debrief: a test suite that only
constrains the rows present cannot detect rows absent.

**Correct.** Drive from `stg_d1_customers` and LEFT JOIN `stg_d1_orders`. Guest orders
then drop out of the join naturally, with no explicit `where customer_id is not null`
needed anywhere.

## Trap 3 — `count(*)` instead of `count(order_id)` under a LEFT JOIN

**Mechanism.** Once the mart correctly drives from customers with a LEFT JOIN, customer 4
produces one join row whose order columns are all NULL. `count(*)` counts that row.

**Naive solution.** `count(*) as order_count`.

**Result.** Dan Wu gets `order_count = 1` instead of 0. Every other row is correct, so
the model looks right at a glance.

**Caught by.** Expected Output comparison only — **no test fires**. `not_null` on
`order_count` passes (1 is not null), `unique` on `customer_id` passes, row count is 4.
This is the quiet one, and it is the closest analogue to the logged blindspot: the error
does not remove a row, it silently mis-states a metric for exactly the row whose metric
matters most.

**Correct.** `count(o.order_id)`, which counts non-NULL values only. Equivalent:
`count(distinct o.order_id)` — but note that here `order_id` is already unique per row,
so `distinct` buys nothing and costs a sort. Worth flagging if Neil reaches for it.

## Non-traps — things that look like traps and are not

- **`relationships` on `stg_d1_orders.customer_id`.** Orders 1006/1007 have a NULL
  `customer_id`, and this test still **passes**. dbt's built-in `relationships` test
  compiles to a child CTE with `where customer_id is not null` before the anti-join. It
  asserts "every non-null value that is present exists in the parent", never "the value
  is present". This is deliberately given verbatim in the problem and is the subject of
  Debrief question 2 — it is a teaching point, not a trap.
- **`status`.** Both `pending` orders are counted in `order_count`, exactly as the
  problem states. There is no status filter anywhere in the correct answer. If Neil adds
  one, that is a requirements-reading miss, not a designed trap: `order_count` would drop
  to 1 for customer 2 and 0 for customer 3, and no test would fire.
- **Email case.** `BOB@Example.com` must be lower-cased, but this is stated explicitly in
  the staging column table. Missing it is caught by review, not by a test.
- **`decimal(10,2)` cast on `amount`.** Stated explicitly. Its purpose is to keep
  `49.90 + 25.10 = 75.00` exact rather than a floating-point 75.00000000000001 that
  fails an eyeball comparison against Expected Output. Not a trap; a fairness measure.
