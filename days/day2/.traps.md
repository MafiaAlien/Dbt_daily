## Trap 1 — the re-exported order (grain)

`ORDER_ID = 5003` appears twice in `raw_d2_orders.csv`:

| exported_at | status | amount |
|---|---|---|
| 2026-03-03 02:00:00 | `pending` | 45.00 |
| 2026-03-04 02:00:00 | `COMPLETED` | 49.00 |

The ERP re-sent the order after it was corrected. Only the 2026-03-04 row is real.

- **Naive solution:** treats the export as 1:1 like a Day 1 seed and passes both rows
  through staging. 12 rows instead of 11.
- **Caught by:** `unique` on `stg_d2_orders.order_id` — hard failure, cannot be missed.
- **Silent damage if the test were absent:** NORAM would be `total_order_count = 7`,
  `completed_order_count = 4`, `gross_revenue_usd = 349.49` — the stale row is `pending`
  so revenue happens to survive, but the counts do not. A solution that dedups on the
  *wrong* side (keeps `min(exported_at)`) gets NORAM `completed_order_count = 3` and
  `gross_revenue_usd = 300.49`, and every test still passes. Only the Expected Output
  table catches that one.

**Secondary point this is really testing:** the problem forbids a `unique` test on the
source's `ORDER_ID` and requires one on `stg_d2_orders.order_id`. A test on a source
asserts what the upstream system guarantees; this system guarantees nothing of the kind.
The uniqueness constraint describes the *model*, which is where the dedup happens.

## Trap 2 — status casing and whitespace (typing/renaming discipline)

`ORDER_STATUS` arrives as `completed`, `Completed`, `COMPLETED`, `completed ` (trailing
space), ` pending` (leading space), `cancelled`, `CANCELLED`, `Cancelled`. Whitespace
was confirmed to survive `dbt seed` into DuckDB (`[completed ]`, `[ pending]`).

- **Naive solution:** passes `ORDER_STATUS` through with a rename only.
- **Caught by:** `accepted_values` on `stg_d2_orders.order_status` with
  `['completed','pending','cancelled']` — fails on 6 of 11 rows.
- **Half-fix that still fails:** `lower()` without `trim()` leaves `'completed '` and
  `' pending'`; `trim()` without `lower()` leaves `'Completed'`, `'COMPLETED'`,
  `'CANCELLED'`, `'Cancelled'`. Both still fail the same test.
- **Silent damage if only the mart filtered:** a solution that leaves staging raw and
  writes `where order_status = 'completed'` in the mart scores EMEA
  `completed_order_count = 1 / 75.25` and Unmapped `0 / 0.00`, because `5004` and `5006`
  never match. Normalisation belongs in staging, once.

## Trap 3 — the unmapped country (the recurring NULL blindspot, new surface)

`ORDER_ID = 5006` has `COUNTRY_CODE = JP`. There is no `JP` row in
`raw_d2_country_region.csv`. This is the deliberate re-exercise of the cumulative
blindspot *"[modeling] NULL-exclusion bugs …"*, sharpened on Day 1 to cover null-padded
rows being counted. Day 1's surface was a LEFT JOIN on the **fact** side; today's is a
LEFT JOIN on a **lookup** side, and it fails in both directions:

- **Naive solution A — `inner join` the lookup:** order 5006 vanishes. Result is 3 rows,
  no `Unmapped` row, and $310.25 of revenue silently disappears. **All 16 tests still
  pass.** Only the Expected Output row count catches it. This is the direct repeat of
  the Day 1 `[dbt]` blindspot *"reviewing one's own solution only against the
  reference's style, never comparing outputs"* — the problem statement warns about row
  count explicitly, in bold, for this reason.
- **Naive solution B — `left join`, no `coalesce`:** `region` is `NULL` for the JP order.
  Caught by `not_null` on `fct_d2_region_revenue.region`. (`unique` on `region` does not
  catch it — a single NULL group is still unique.)

## Trap 4 (direction, not a fourth trap class) — which side drives the mart

`MX → LATAM` exists in the lookup and **no order was ever placed from MX**. The stated
grain is "one row per region that appears in `stg_d2_orders`", so LATAM must not appear.

- **Naive solution:** drives the mart from `stg_d2_country_region` and left-joins orders
  onto it — the Day 1 trap 2 shape, inverted.
- **Result:** a 5th row, `LATAM`, with `total_order_count = 0` and
  `gross_revenue_usd = NULL`, which trips `not_null` on `gross_revenue_usd`. If the
  solution coalesces the sum, the test passes and only the row count exposes it.

## Recurrence check (deliberate repetition, not counted as a new trap)

`AU → APAC` has exactly one order, `5011`, and it is `cancelled`. So APAC's
`gross_revenue_usd` is a `sum()` over an **empty** set → `NULL`, and must be `0.00`.

This is Day 1's trap 1 replayed verbatim, and Day 1's first key takeaway is exactly the
asymmetry it depends on: `count()` over an empty/all-null group returns `0`, `sum()`
returns `NULL`. Caught by `not_null` on `gross_revenue_usd`. Note `completed_order_count`
needs no `coalesce` for the same reason. Whether Neil coalesces both (harmless but shows
he has not internalised the asymmetry) or only the sum is worth grading in the digest.

Also flavour, not a trap: `ORDER_ID = 5004` is `completed` with a missing `AMOUNT_USD`,
sitting in EMEA alongside `5008` (75.25). `sum()` skips the NULL, so EMEA is 75.25 with
`completed_order_count = 2`. The requirement is stated explicitly, and the naive
behaviour is already correct — it is there so the "missing amount contributes 0" rule is
exercised without being a second NULL trap.

## What is NOT a trap here

- The `sources.yml` shape is fully specified in the problem, including the ban on a
  `database:` key. The ban is real and load-bearing — the reference project runs against
  `practice_ref.duckdb`, so a hard-coded `database: practice` would break Stage 4 — but
  it is stated, not hidden.
- Freshness reporting `ERROR STALE` is expected and stated. Confirmed:
  `1 of 1 ERROR STALE freshness of erp.orders`.
