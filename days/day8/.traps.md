# Day 8 — trap notes

**Read only in `/review 8` phase 3 (after phases 1–2 ran in that conversation) and in
`/digest 8`.**

All behaviour below was verified on 2026-09-30 against dbt-core 1.12.0 / dbt-duckdb
1.10.1, in a throwaway project in the container's `/tmp` (deleted afterwards). Seeds are the
ones in `dbt_practice/seeds/day8/`. The correct design ran `PASS` on all three runs, and the
snapshot, dim and agg matched `## Expected Output` exactly.

Relevant dbt internals (from `macros/materializations/snapshots/{strategies,helpers}.sql`):
- `check` strategy: `updated_at = config.get('updated_at') or snapshot_get_time()`. So
  without `updated_at`, `dbt_valid_from` / `dbt_valid_to` are run times. With it, they are
  that column's values.
- `hard_deletes: new_record`: the deletion row copies the snapshotted row's columns, sets
  `dbt_valid_from = snapshot_get_time()`, and **`dbt_valid_to` = the old row's
  `dbt_valid_to`, i.e. NULL**, with `dbt_is_deleted = 'True'`. `dbt_is_deleted` is
  **VARCHAR** `'True'` / `'False'`, not boolean. When the key reappears, the deletion row is
  closed and a new row is inserted, even if every tracked column is identical. A key that
  stays absent gets no second deletion row.
- Deletion timestamps are always `snapshot_get_time()`, whatever the strategy.

Correct config: `strategy: check`,
`check_cols: [department_code, job_title, salary_band]`, **no** `updated_at`,
`hard_deletes: new_record`, `unique_key: employee_id`.

Expected test count, V1–V12: **42**. V1 9, V2 3, V3 7, V4–V7 4, V8 4, V9 8, V10 1, V11 5,
V12 1.

## T1 — Change detection: which strategy, and which columns (FAILING TEST)

The feed has two bait columns. `RECORD_UPDATED_AT` looks like Day 7's `updated_at` but is
not bumped by the bulk reorg (E03 and E04, OPS→LOG, batch 2), and *is* bumped by a
correction that must create no version (E02's name, batch 3). `LAST_LOGIN_AT` changes every
night for nearly everyone.

**Naive (a): `strategy: timestamp`, `updated_at: record_updated_at`** (Day 7's muscle memory).
Verified result after run 3:
- E03 stays `OPS` and open, and the reorg is never recorded. **V6 fires** (tracked mismatch,
  E03 open row OPS vs dump LOG). E04's OPS row is closed only by its termination, so E04's
  deletion record carries **OPS**, not LOG. In the agg, OPS terminations become 1 and LOG 0.
- E02 gets a second version at 2026-05-02 11:00, for a name change only. **V7 fires.**
- Mixed clocks: E07's first version is closed at the run-2 wall time (2026-09/10), the
  deletion record runs from the run-2 wall time to **2026-05-02 15:00** (a negative window),
  and the rehire opens at 2026-05-02 15:00, which lies inside the first version's window.
  **V5 fires** (empty/negative window plus overlap).
- `dbt_valid_from` values are business times, so the R-label capture mislabels everything.

**Naive (b): `strategy: check`, `check_cols: all`** (the lazy default). Verified: E01, E02,
E03 and E05 each get one redundant version per night of login changes (E02 also on the name
change). Run 2: **V7 `FAIL 2`**. Run 3: **V7 `FAIL 5`**. Snapshot row counts 7 / 14 / 21
instead of 7 / 12 / 16. Including `full_name` or `last_login_at` in an explicit list
produces a smaller version of the same failure.

**Naive (c): `check` plus `updated_at: record_updated_at`** ("get business time back").
Verified: E03 and E04's reorg versions get `dbt_valid_from` = the *unchanged*
`record_updated_at` (2026-01-15 08:30 / 2025-11-20 11:00), so the OPS rows close at their
own `valid_from` and become **zero-width windows**, and both rows of each pair share a
`dbt_scd_id`. E07's deletion record again has `valid_from` (wall clock) > `valid_to`
(2026-05-02 15:00). **V5 fires** on the empty windows. Day 7's V6 shape (no empty-window
check) would not catch it, which is why the brief says to add it.

Which test catches each: (a) V5 + V6 + V7; (b) V7; (c) V5. V4 stays green in all three.
Exactly one open row per key survives every variant, which is the point of debrief Q1.

## T2 — The termination record is "open" (FAILING TEST)

Under `hard_deletes: new_record`, a terminated employee's open row (`dbt_valid_to is null`)
**is the termination record**. Day 7's "current = `dbt_valid_to is null`" stops being true.

**Naive:** `is_current = dbt_valid_to is null` (or the dim filtering only on that). Verified:
the dim gets **8 rows** (E04 LOG and E06 SALES added), and **V10 `FAIL 2`** on runs 2 and 3
(run 1 green, since nobody has been terminated yet). This is the mart→staging direction. V9's
`unique` stays green, because each terminated employee has only one open row. The agg
inflates consistently (LOG 2, SALES 2), so **V12 stays green**: the totals tie out to a
wrong dim.

Related forms:
- **No `hard_deletes` at all** (default `ignore`): E04 and E06 stay open as live versions
  forever. **V6 fires** (live version not in dump). Under the timestamp strategy the rehired
  E07 still versions, because `record_updated_at` was bumped. `dbt_is_deleted` does not exist,
  so V3 errors at compile time and terminations cannot be counted.
- **`hard_deletes: invalidate`**: windows are closed but no termination rows exist (12 rows
  after run 3 under check). `dbt_valid_to is null` *is* correct for the dim in this mode,
  but `terminations_to_date` cannot be derived, there is no `dbt_is_deleted` column, and the
  snapshot tables do not match. A legitimate design that fails the stated requirement
  ("a termination is a row").
- **Type gotcha:** `dbt_is_deleted` is VARCHAR. `= 'True'` works, and so does
  `cast(... as boolean)` in DuckDB. `where not dbt_is_deleted` depends on implicit casting
  and is worth asking about in review. V3's `accepted_values` must use the strings.
- **Rehire:** E07's open row after run 3 is a normal version (`False`). A dim that excludes
  "anyone with a termination record" drops E07, and V10 fires in the staging→mart direction,
  his historically weak side.

## T3 — Overwrite columns read from the snapshot (SILENT)

The snapshot stores `full_name` and `last_login_at` *as they were when the version was
written*. Because they are not in `check_cols`, they are never refreshed on an unchanged
version. The dim must read them from `stg_d8_employees` (the latest dump).

**Naive:** the dim takes all columns from the snapshot's current row. Verified: all 12 tests
stay green on all three runs (V10 compares only keys; V9 only nullness). Wrong cells after
run 3:

| employee | column | naive (snapshot) | expected (dump) |
|---|---|---|---|
| E02 | full_name | Ben Okafor | Benedict Okafor |
| E02 | last_login_at | 2026-04-30 09:12:00 | 2026-05-02 09:05:00 |
| E03 | last_login_at | 2026-05-01 15:02:00 | 2026-05-02 14:48:00 |
| E05 | last_login_at | 2026-05-01 16:25:00 | 2026-05-02 11:37:00 |

E01, E07 and E08 are right by accident: their current version was written in run 3. That is
how half the table hides the bug, the same shape as Day 4's fan-out hiding on SL03/SL04.
Only a cell-by-cell comparison, or a V10 extended to compare overwrite columns, catches it.

An over-correction to watch for: adding `full_name` to `check_cols` "so the snapshot stays
fresh". That turns T3 into T1. E02 gets a redundant version and V7 fires.

## Secondary — department summary, Day 1 / Day 3 recurrence (FAILING TEST via V12)

Not one of the three designed traps. It is a re-exercise of the escalated blindspot
`[modeling] counting at a grain that is not the entity being counted`.

- **`count(*)` under `departments LEFT JOIN dim`**: OPS (dissolved by the reorg) gets
  `current_headcount = 1`, and ENG / OPS get `terminations_to_date = 1`. Sums become 7 / 5.
  **V12 fires.** Day 1 trap 3, verbatim.
- **One join for both aggregates** (`departments ⟕ dim ⟕ termination rows`, then count): a
  fan-out. FIN has 2 current × 1 termination, so `count(*)` gives 2 / 2. `count(distinct
  employee_id)` rescues headcount and also hides it. **V12 fires** on the `count(*)` form.
- **Termination department taken from the employee's *first* version** (or from the dump):
  E04 lands in OPS instead of LOG. Totals still tie (3), so **V12 is green, silent**. The
  expected agg has OPS 0 / 0 and LOG 1 / 1.
- **Type drift:** `count()` returns BIGINT in DuckDB, and the contract says `integer`. Cell
  comparison including types catches it. No test does.
