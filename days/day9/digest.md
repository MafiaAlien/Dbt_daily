- Key takeaways:
  - 全量 dump 和 append-only 日志的读法相反：dump 是"那一晚的完整画面"，按 `batch_id = N` 读；日志是"截至那一晚的累计"，按 `batch_id <= N` 读。把 `=` 套到日志上，晚到的 payment 就找不到自己的 invoice（batch 1 的 I01 不在 batch 2 的 staging 里），于是 `relationships` FAIL，int 和 mart 被 SKIP，mart 冻结在 run 1。增量模型"只重算一部分"只能在**一处**做：mart 的 `is_incremental()` 分支里，用 `{{ this }}` 推导回看窗口；上游必须读全量。在 staging 再按 batch 切一刀，等于用一个没推导过的谓词，替换掉了推导过的那个。
  - Point-in-time 归属有两条互相独立的推导。模型用区间包含：`dbt_valid_from <= ts and (dbt_valid_to is null or ts < dbt_valid_to)`。测试用"`dbt_valid_from <= ts` 的版本里取最新一条"：`row_number() over (partition by invoice_id order by dbt_valid_from desc) = 1`，完全不读 `dbt_valid_to`。V6 保证版本首尾相接，此时两者等价，所以只要出现分歧，就只可能是模型的 bug。测试有两种写坏法：一是和**所有**更早的版本比较（I11 会去比 C01 的 STARTER 旧版本，正确数据上也红）；二是用严格的 `>`（I05 正好落在 09-03 14:00 的边界上，覆盖它的 GROWTH 版本被排除在外）。另外，从 staging 取"当前 plan"就是 T3(a)：run 1 时每个客户只有一个版本，所以碰巧全对；从 run 2 起，I01 和 I04 就被归错了。
  - 增量模型有两条代码路径，而 run 1 和 `--full-refresh` 走的都是**非增量**那条。所以 `is_incremental()` 分支里的错误，要到第二次运行才第一次被编译、执行。例如 `strftime(ts, '%Y-%m-%d')` 返回的是 VARCHAR 不是 DATE，`max(varchar) - interval '4 days'` 会报 `Binder Error: -(VARCHAR, INTERVAL)`：run 1 全绿、run 4 也全绿，只有 run 2 / 3 才会报错。取日期要用 `cast(ts as date)`；带回看窗口的谓词，必须在至少一次真正的增量运行上亲眼看过。

- Parking lot additions: `merge` vs `delete+insert` when a (date, plan) group moves (debrief Q2, unanswered) — `delete+insert` deletes only the keys present in the new batch, and dbt-duckdb's `merge` by default updates matched keys and inserts new ones without deleting target rows absent from the source, so under `unique_key = ['invoice_date', 'plan_code']` either strategy leaves a stale row when a re-attributed invoice moves plan, while `unique_key = 'invoice_date'` under `delete+insert` replaces the whole date. Snapshot strategy for attribution-only history (debrief Q3, unanswered) — `check` with `check_cols: [plan_code]` would have skipped C02's name-correction version, but it stamps `dbt_valid_from` with the snapshot's run time, which falls after every invoice it should cover, so with a correct as-of predicate no invoice matches any version; `timestamp` on a trustworthy `updated_at` is the only strategy whose windows are application time.
