## T1 — chasm fan-out: two independent "many" sides of one invoice

**Class:** grain / fan-out (escalated blindspot; Days 1, 3, 4 hit; Days 5–8 avoided in
code, never articulated). **New shape:** not header-vs-line, but **two child tables of the
same parent**, lines and payments, both many-to-one to the invoice. "Aggregate the many
side first" has to be applied twice, separately, before either join. Joining both and then
aggregating multiplies each side by the other's row count.

**Naive solution:** `stg_d9_invoices ⟕ stg_d9_invoice_lines ⟕ stg_d9_payments`, then
`group by invoice_id` with `sum(l.amount_usd)` and `sum(p.amount_usd)`.

**What it produces** (after run 3; lines × payments per invoice):

| invoice | lines | payments | billed (naive / right) | collected (naive / right) |
|---|---|---|---|---|
| I01 | 2 | 2 (P01, P03) | 123.00 / 61.50 | 123.00 / 61.50 |
| I03 | 3 | 2 (P02, P09) | 2172.50 / 1086.25 | 3258.75 / 1086.25 |
| I04 | 2 | 1 | 219.00 / 219.00 | 438.00 / 219.00 |
| I05 | 2 | 1 | 204.00 / 204.00 | 408.00 / 204.00 |
| I07 | 1 | 2 (P06, P07) | 98.00 / 49.00 | 49.00 / 49.00 |
| I08 | 2 | 1 | 95.75 / 95.75 | 191.50 / 95.75 |
| I11 | 2 | 1 | 62.00 / 62.00 | 124.00 / 62.00 |

Invoices with one line and at most one payment (I02, I06, I09, I10, I12) are right, which
is how it hides. Note the asymmetry: I07 inflates *billed* only, I04 / I05 / I08 / I11
inflate *collected* only, I01 / I03 inflate both. `count(distinct)` cannot rescue a sum.

**Which test catches it:** **V12** (tie-out to staging), from **run 1**. Batch 1 has one
payment each for I01 (P01) and I03 (P02), so run-1 billed is still right, but collected is
inflated: I01 30.00 × 2 lines = 60.00, I03 500.00 × 3 lines = 1500.00, so the
`sum(collected_usd)` tie-out fails. Billed inflates from run 2 (I01's and I07's second
payments). V12 reads staging precisely so that a fan-out inside the int cannot cancel out:
a tie-out against the int would pass.

**Correct shape:** pre-aggregate lines to `invoice_id` and payments to `invoice_id` in two
separate CTEs, then left-join both to the invoice header (one row per invoice on each
side). `coalesce(collected, 0)`.

`## Plan` part 1 ("how many rows of each relation can match one invoice") is the line that
names this before it is written: lines 1..n, payments 0..n, **and both at once**.

## T2 — late payments: the incremental predicate must reopen closed days

**Class:** incremental / late-arriving data (Day 5 watermark boundary, Day 6 lookback).
**New shape:** the late rows are not facts of the mart's grain but a **child measure**
(payments) of facts already published. The invoices themselves are never late, so a
watermark on invoices looks complete.

**Data that discriminates:**

- Run 2 (target `max(invoice_date)` = 09-02): P03 (I01) and P04 (I02) are for
  **2026-09-01**, so run 2 must recompute 09-01 → needs lookback ≥ 1 day.
- Run 3 (target max = 09-04): P08 (I04) and P09 (I03) are for **2026-09-02**, at the SLA
  edge (loaded 09-06 = invoice_date + 4) → needs lookback ≥ 2 days on this data.

**Naive solutions and what they produce:**

- `where invoice_date > (select max(invoice_date) from {{ this }})` — run 2: 09-01 GROWTH
  collected stays 0.00 (should be 199.00), 09-01 STARTER stays 30.00 (61.50). Run 3: 09-02
  GROWTH stays 0.00 (219.00), 09-02 SCALE stays 500.00 (1086.25). Plus 09-01 still wrong.
- `>=` max (re-processes only the last day) — same misses (09-01 and 09-02 are both older
  than max).
- A 1-day lookback — run 2 right; run 3 misses 09-02 (GROWTH 0.00, SCALE 500.00).
- Tempting "fix" that changes the metric: bucketing payments by `date(paid_at)` so late rows
  land on new days. Totals still tie, so V12 passes. Every collected cell is wrong against
  the contract ("against those invoices, whatever date they were paid"). Silent.

**Which test catches it:** **V12**, the collected tie-out, on run 2 (and run 3). **Run 4**
(full-refresh equivalence) also exposes it cell by cell.

**Correct derivation (any schedule):** a payment in a load dated `L` belongs to an invoice
dated ≥ `L − 4`. The target's `max(invoice_date)` = M was loaded no later than the
previous load, and the next load is on or after M's date, so `L ≥ M`, and the safe
predicate is `invoice_date >= M − 4 days` (equivalently `> M − 5`). `M − 3` relies on the
next load being strictly after M's date, which "every 6 hours" (debrief Q1b) breaks. On this
data anything ≥ 2 days passes. The derivation is graded in `## Plan` part 3, not just the
cells. Debrief Q1a asks why the minimal 2-day lookback is wrong: it's fitted to the data, not
derived from the SLA.

Config notes for the review: `unique_key` `['invoice_date','plan_code']` or
`'invoice_date'` both produce the expected tables *with correct attribution* (each
date's set of plans never changes). The dbt-duckdb default `incremental_strategy` is
`delete+insert`. The int must be read in full by the incremental branch's filter, not
pre-filtered on invoice batch.

## T3 — point-in-time attribution to a timestamp snapshot: current plan, boundary, open end

**Class:** SCD2 interval join (Day 7 T1–T3: half-open boundary, NULL open end, current
tier instead of tier at event time). **New shape:** it is now inside an **incremental** DAG,
so a wrong attribution does not just put the wrong label on a cell. Depending on the
`unique_key`, it can leave **stale rows** that the incremental merge never deletes.

**Sub-traps and what each produces:**

- **(a) Current plan** — `join snap on customer_id and dbt_valid_to is null`. PIT-wrong
  invoices after run 3: **I01** (C01 STARTER at 09-01, current GROWTH) and **I04** (C04
  GROWTH at 09-02, current STARTER). Run 1 is right (no changes yet). Run 2 recomputes 09-01
  (if T2 is handled): I01 → GROWTH. With `unique_key = ['invoice_date','plan_code']` the
  run-1 row (09-01, STARTER) is never deleted → **stale row** survives, (09-01, GROWTH)
  becomes count 2 / billed 260.50 → V12 billed tie-out fails (double-counted I01). With
  `unique_key = 'invoice_date'` the whole date is replaced → totals tie, **silent**, cells
  wrong: no (09-01, STARTER) row; (09-01, GROWTH) 2 / 260.50 / 260.50 / 0.00. Run 3 does the
  same to I04 on 09-02 (→ STARTER). Run 4 (full refresh) with current-plan attribution
  is wrong for both dates as well. V9 (independent attribution) catches it on the int in
  every case from run 2 onward.
- **(b) Inclusive boundary** — `between dbt_valid_from and dbt_valid_to` (or `<=` on the
  upper end). **I05** is invoiced at exactly `2026-09-03 14:00:00`, C01's STARTER→GROWTH
  edit; **I12** at exactly `2026-09-05 11:00:00`, C02's name-correction edit. Each matches
  two versions → the int has two rows for I05 (STARTER and GROWTH) from run 2 and two for
  I12 (both GROWTH) from run 3. Caught by V7 `unique` on `invoice_id`, V8 (exactly once),
  and V12 (billed/collected/count inflated). I12 is the one where both versions have the
  same plan, so the label looks right and only the count gives it away.
- **(c) NULL open end** — `invoiced_at < dbt_valid_to` with no `is null` branch. Every
  invoice whose version is still open is unmatched: inner join drops them (V8, V12 fail);
  left join leaves `plan_code` NULL (V7 `not_null` fails). Most invoices are in open
  windows, so this is loud.

**Which test catches it:** V9 (all three sub-traps, independent derivation that never reads
`dbt_valid_to`), V7 / V8 (b, c), V12 (a with composite key, b, c). Sub-trap (a) with a
date-only `unique_key` passes everything except V9, so a V9 that reuses the model's own
join predicate makes (a) fully silent; that is the Day 7 blindspot ("a test that reuses the
model's predicate inherits the model's bug"), re-exercised.

**Correct predicate:** `i.customer_id = s.customer_id and i.invoiced_at >= s.dbt_valid_from
and (s.dbt_valid_to is null or i.invoiced_at < s.dbt_valid_to)`.

**Snapshot config** (not a trap, but where a wrong choice cascades into T3): the brief pins
`dbt_valid_from` to application time, so `strategy: timestamp`, `updated_at: updated_at`.
Choosing `check` on `plan_code` sets `dbt_valid_from` to the run's wall-clock time
(October 2026), after every invoice → with a correct PIT predicate **no invoice matches any
version** (all `plan_code` NULL / all rows dropped); loud. It would also skip the C02 name
version, so the snapshot would show 7 rows after run 3, not 8, and V6 still passes.
