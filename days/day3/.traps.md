## Trap 1 — config precedence: the folder-level lever is the wrong lever

**Setup.** `dbt_project.yml` gives `day3:` a day-level `+materialized: view` and a more
specific `marts: +materialized: table`. The problem requires `fct_d3_plan_usage` to be a
**table** and `dim_d3_plan_current` to be a **view** — two different materializations
inside the same directory, which a directory-level config cannot express.

**What a naive solution does.** Two failure shapes:

1. *Leaves it alone.* `dim_d3_plan_current` inherits `table` from the `marts:` block and
   is built as a BASE TABLE.
2. *Reaches for `dbt_project.yml`.* Changes `marts: +materialized: view`, which is the
   most visible lever and the one already in front of them. `dim` becomes correct and
   **`fct_d3_plan_usage` silently becomes a view.** The problem forbids this edit, so
   doing it is also a spec violation, but the interesting part is that it does not look
   wrong — both marts build, every generic test passes.

The only correct fix is an in-model `{{ config(materialized='view') }}` in
`dim_d3_plan_current.sql`. The lesson is the precedence order: in-model `config()` beats
a specific path in `dbt_project.yml`, which beats a general path, which beats the
project default.

**Which test catches it.** `assert_d3_materializations` — shape 1 returns the row
`(dim_d3_plan_current, VIEW, BASE TABLE)`, shape 2 returns
`(fct_d3_plan_usage, BASE TABLE, VIEW)`. Both are `FAIL 1`.

**Why it needs a singular test at all.** Nothing in dbt's generic test library looks at
`table_type`. `unique`, `not_null`, `accepted_values` and `relationships` all pass
identically whether a model is a view or a table — that is the whole reason this trap is
invisible without the catalogue query.

## Trap 2 — "intermediate" is not a materialization

**Setup.** The `day3:` block has **no `intermediate:` key**. The day-level
`+materialized: view` therefore applies to `int_d3_billable_usage`, and dbt's own default
would also be `view`. So doing nothing produces a working, correct-looking view.

**What a naive solution does.** Writes `int_d3_billable_usage.sql` with no config block,
gets a view, and every other test passes — the fact table's numbers are right, because a
view and an ephemeral CTE compute the same rows. Nothing about the *data* is wrong. What
is wrong is that a relation exists that the design says must not.

**Which test catches it.** `assert_d3_intermediate_is_ephemeral` returns
`(int_d3_billable_usage, VIEW)` → `FAIL 1`.

**The second-order trap, and this one bites hard.** If he builds it as a view first and
*then* adds `{{ config(materialized='ephemeral') }}`, **dbt does not drop the existing
relation.** The old view stays in `practice.duckdb` and the test keeps failing on a ghost
with correct-looking code. The problem file warns about this explicitly and gives the
`rm -f practice.duckdb` rebuild, so a failure here is a failure to read the warning — but
expect it to cost time regardless. Watch for it in the `/review` execution phase: if his
run is red on this test, check whether his *code* is right before concluding anything.

**Verified during problem setting:** a probe project confirmed (a) generic tests do run
against ephemeral models — dbt inlines the CTE into the test query, so the
`intermediate/schema.yml` `unique`/`not_null` on `event_id` are real tests, not decoration;
(b) an ephemeral model leaves no row in `information_schema.tables`; (c) the
`-- depends_on:` comment attaches a singular test to the DAG so `path:models/day3` selects
it. The suite was proven to PASS when ephemeral and FAIL 1 when switched to view.

## Trap 3 — `count` vs `sum` over the same rows (recurring, third occurrence)

**This is a deliberate re-run of a blindspot.** Day 1 trap 3 (`count(*)` under a LEFT
JOIN scoring a customer with zero orders as 1) and Day 2 trap 5 (`sum()` over an empty
completed set) are the same pattern. Day 2's code got the right answer via a blanket
`else 0` applied identically to the count and the sum, which is precisely the signal that
the asymmetry is not internalised. The Day 2 digest says so. This day builds a shape
where one blanket rule cannot be right for both columns.

`billable_event_count` and `billable_units` are aggregated over **the same set of rows**
and fail in **different** ways.

**Two plans are constructed to separate them:**

| plan | rows in `int_d3_billable_usage` | breaks what |
|---|---|---|
| `scale` (S004 active, S007 churned) | **zero** — S004's only events, E0008 and E0009, are `is_billable = false`; S007's E0013 is billable but churned | the *count* |
| `enterprise` (S006 active) | **two** — E0011 and E0012, both billable, both with `units` NULL | the *sum* |

**What a naive solution does.**

- `count(*)` under a LEFT JOIN → `scale` gets `billable_event_count = 1`, counting the
  null-padded row. Expected is `0`. **Verbatim Day 1 trap 3.**
- `count(u.units)` → `enterprise` gets `billable_event_count = 0`, because `count(expr)`
  skips NULLs. Expected is `2`. The events exist; only their quantity is missing. Correct
  is `count(u.event_id)`.
- `sum(u.units)` with no outer `coalesce` → `scale` gets NULL (no rows) **and**
  `enterprise` gets NULL (all values NULL). Expected is `0` for both.

The instructive part: `count` and `sum` need *different* defences over the same rows.
`count(event_id)` is already right with no coalesce anywhere; `sum(units)` needs
`coalesce(sum(...), 0)`. A single blanket `case when ... then x else 0 end` applied to
both — Day 2's habit — gets the sum right and, if paired with `count(*)`, still gets the
count wrong for `scale`.

**Which test catches which half.**

- The `sum` half: `not_null` on `billable_units` in `marts/schema.yml` → `FAIL 1` (or 2).
- The `count` half: **no test catches it.** `billable_event_count` is non-null and an
  integer whether it says 0, 1 or 2. It shows up only by comparing `fct_d3_plan_usage`
  against the Expected Output table. This is the "row count / cell values are part of the
  answer" discipline from Day 2, and it is why the problem file says a solution can pass
  every generic test and still be wrong here.
