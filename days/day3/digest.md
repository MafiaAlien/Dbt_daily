### Day 3 — materialization trade-offs: view vs table vs ephemeral, and config precedence (2026-08-11)
- Problem: build three staging views, one ephemeral intermediate, and two marts in the same `marts/` directory that must be different materializations — a table and a view — with `dbt_project.yml` frozen, plus a fact table whose `billable_event_count` and `billable_units` are aggregated over the same rows and fail in different ways.
- Traps: (1) config precedence — a directory-level `marts: +materialized: table` cannot express two materializations inside one directory, and the visible lever (editing `dbt_project.yml`) silently flips `fct_d3_plan_usage` to a view — **caught in code** (`config(materialized='view')` on `dim_d3_plan_current`, both singular tests green), half-caught in review: D3 discussed config placement but stated the reference's behaviour incorrectly and never named the precedence order. (2) `intermediate` is not a materialization — the `day3:` block has no `intermediate:` key, so doing nothing yields a working view — **caught in code** (`ephemeral` set, no relation left in `information_schema`, second-order stale-relation trap not triggered); not mentioned in review at all. (3) `count` vs `sum` over the same rows, third run of a known blindspot — the count half (`scale` = 0, `enterprise` = 2) **caught in code and correct**, sourced from the intermediate with an outer `coalesce`; the sum half **hit**, but in an unforeseen shape: rather than a missing `coalesce` producing NULL, `billable_units` was computed over an entirely different row set — a `subscriptions LEFT JOIN usage_events` fan-out guarded by `is_billable is not null`, a null check that is true for every row and filters nothing. The trap's designated catcher (`not_null` on `billable_units`) never fired, because a blanket `else 0` kept the column non-null. (4) Not a designed trap, and the largest error of the day: the same fan-out CTE computed `subscription_count` and `active_subscription_count`, inflating every plan by its event count — 8 wrong cells, missed in code and absent from the verdict entirely. Net result: `dbt build --select path:models/day3` returned **37/37 PASS with 8 of 16 fact-table cells wrong**; `dim_d3_plan_current` matched Expected Output exactly, `fct_d3_plan_usage` matched only `plan_code`, the row count, and `billable_event_count`.
- Verdict scorecard: 2 right / 3 wrong / 1 not settled. Right: D1 called the intermediate's filter predicate equivalent — correct, `WHERE x` and `x IS TRUE` both admit only TRUE and both projects produced the same 8 rows; "reference bugs I claim: none" — correct and a clean no-false-alarm, the reference matched Expected Output cell for cell in both marts. Wrong: D2 named the wrong column (`billable_event_count` was the one column taken from the intermediate, and it was right; `billable_units` was the recomputed one), set **Call: equivalent** while its own **Why** argued the opposite, and quoted its own code as `is_billable = True` when the file says `is_billable is not null` — the mis-remembered line is exactly the bug, and "How execution would settle it: no idear" follows from it. "Would ship: neither" — the reference was shippable, rejected on D3's false premise. "Could not settle by reading: none" — contradicted by "no idear" three lines above. Not settled: D3, which execution cannot decide (both versions build identically) and whose premise that the reference "skips the definition of materialized config" is false — the reference writes `config()` on exactly the two models whose inherited value contradicts the requirement. `My own solution` named the right model and the wrong mechanism, and did not contain the fan-out.
- Key takeaways:
  - 维度计数必须在**维度自己的 grain 上聚合完**再 left join 事实表。`subscriptions left join usage_events` 之后的 CTE，grain 已经是 (订阅×事件)，此时 `count(*)` 数的是 join 行数，每个订阅按它的事件条数被放大；`sum(case when status='active' then 1 else 0 end)` 同样被放大。正确形状是参考解的两段式：先 `group by plan_code` 把订阅聚成一行，再把用量聚合 left join 上去 —— 一次 join 只允许一边是"多"。
  - boolean 列上写 `x is not null` 是**空值检查**，不是真值检查；只要该列非空（而 `not_null` test 正保证了它非空），这个谓词恒为真，一行都滤不掉。要过滤真值只有 `where x` 或 `x is true`。同理 `count(x)` 跳过 NULL 而 `count(*)` 不跳 —— 谓词和聚合函数各有各的 NULL 语义，不能靠一条统一规则覆盖。
  - materialization 优先级：in-model `{{ config() }}` > `dbt_project.yml` 里更具体的路径 > 更一般的路径 > 项目默认。同一个目录里要两种物化时，目录级 config 表达不了，只能用 in-model override —— 这是它唯一正当的用途。反过来，在**每个**模型里都写死 config，会让一次有意的项目级变更（比如把所有 marts 改成 incremental）静默失效：你以为改了，实际一个都没生效。
- Recurring-pattern check: four repeats, all escalated. (1) The fan-out is the **third occurrence** of counting at a grain that is not the entity being counted — Day 1 trap 3 counted a null-padded LEFT JOIN row as one order, Day 2 trap 1 was the same family on the dedup side, and here a fan-out join inflated two dimension counts at once. Day 1's sharpening covered null-padded rows being counted; it did not cover *duplicated* rows being counted, and the blindspot entry is widened accordingly. (2) "Could not settle by reading: none" written above an explicit "no idear" — **third verbatim occurrence** (Day 1, Day 2, Day 3). This is now the most reliably repeated single error in the log. (3) The `My own solution` section, added after Day 1 and already escalated after Day 2, produced its third consecutive miss: right model, wrong mechanism, and silent on the largest defect. (4) `days/day3/notes.md` left with two headings and no content — **third occurrence**, and the second consecutive day where the whole file is empty; the four debrief questions, including two trade-off questions, are unwritten deliverables. New pattern, first named this day: substituting a blanket rule for case-by-case reasoning. Day 2 applied one `else 0` to both the count and the sum; Day 3 wrote `config()` into all six models "no matter how they are set in dbt project yaml". The blanket rule was right on materialization and wrong on aggregation, which is precisely why the habit is invisible until it costs something. Second new pattern: describing one's own code from memory instead of re-reading it — D2 quoted a predicate that is not in the file, and that gap is the whole reason the bug survived the review.
