# Day 5 — trap notes

**Read only in `/review 5` phase 3 (after phases 1 and 2 have run in that conversation)
and in `/digest 5`.**

Design principle this day: **every trap survives a green build.** All six tests pass on
every naive variant below except trap 2. The only thing that separates a correct mart
from a wrong one is comparing the run-1 and run-2 tables cell by cell — which is the
`[dbt] reviewing one's own solution ... never comparing outputs` blindspot, four
occurrences, at its purest.

Correct output is in `## Expected Output`: 5 rows after run 1, 8 rows after run 2.
All naive values below were computed against the loaded seeds, not derived by hand.

---

## Trap 1 — the watermark boundary: `>` where it must be `>=`

**The setup.** 2026-06-03 is delivered in two pieces. Batch 1 carries its morning
shipments (S008 WH-A, S009 WH-C); batch 2 carries the rest of the same day (S010 WH-A,
S011 WH-B) *plus* restatements of S008 and S009. So batch 2's minimum `ship_date` equals
batch 1's maximum `ship_date`. The feed guarantee in the problem says a batch never goes
*earlier* than that — it says nothing about equal, and equal is the case that bites.

**What a naive solution does.**

```sql
{% if is_incremental() %}
where ship_date > (select max(ship_date) from {{ this }})
{% endif %}
```

The run-2 window becomes `> 2026-06-03`, i.e. 2026-06-04 only. The 06-03 rows written by
run 1 are never revisited and stay frozen at their run-1 values.

**Resulting table — 7 rows instead of 8:**

| ship_date | warehouse | got | expected |
|---|---|---|---|
| 2026-06-03 | WH-A | 1 / 0 / 10.00 / 3 / 6.500 | 2 / 2 / 24.25 / 7 / 9.650 |
| 2026-06-03 | WH-C | 1 / 0 / 13.50 / 4 / 3.000 | 1 / 1 / 11.75 / 4 / 3.000 |
| 2026-06-03 | WH-B | **row absent** | 1 / 1 / 9.50 / 2 / 1.500 |

The five 06-01/06-02/06-04 rows are correct. **No test fires.** `unique` on the grain
holds, `shipment_count >= 1` holds, `delivered_count <= shipment_count` holds, nothing is
NULL. The run summary is `ERROR=0 WARN=0`.

**What catches it:** the run-2 snapshot comparison, and the equivalence check —
`--full-refresh --vars '{d5_batch: 2}'` recomputes 06-03 correctly and therefore disagrees
with the incremental table. That is exactly why the equivalence check is in the pass
condition.

**Correct answer:** `>=`, which recomputes the whole of the boundary day, made safe by
`unique_key` replacing the rows it recomputes. `>` and `>=` are not stylistic variants
here: `>` is only safe if the model has no `unique_key`, in which case it is wrong for a
different reason.

## Trap 2 — `>=` with no `unique_key` (the failing test)

**What a naive solution does.** Gets the boundary right, `materialized='incremental'`,
`is_incremental()` filter with `>=`, and no `unique_key` in the config — or a
`unique_key` naming a column that is not the grain of the model.

With no `unique_key`, dbt-duckdb's `default` strategy resolves to `delete+insert`
(`duckdb__get_incremental_default_sql` → `get_incremental_delete_insert_sql`), and with
no key there is nothing to delete on — the run degenerates to a plain append.

Run 2's window (`ship_date >= 2026-06-03`) produces 5 rows: 06-03 WH-A/WH-B/WH-C and
06-04 WH-A/WH-B. They are **appended** to run 1's 5 rows.

**Resulting table — 10 rows**, with `(2026-06-03, WH-A)` and `(2026-06-03, WH-C)` each
appearing twice, once with run-1 values and once with run-2 values.

**Test that catches it: V4**, the singular test asserting no two rows share
(`ship_date`, `warehouse_code`). It returns 2 rows and fails the run-2 build. This is the
day's mandatory failing-test trap.

V5 and V6 stay green — both duplicates are individually valid rows.

**Note for the three-way compare:** if he wrote V4 as a generic `unique` test on
`ship_date` alone it would *also* fail here, for the wrong reason — that test is wrong on
correct output too (06-03 legitimately has three warehouses). Check which of the two he
wrote; a green run-1 build rules out the broken version, since run 1 already has two rows
on 2026-06-01 and two on 2026-06-03.

## Trap 3 — the restatement: the header feed is not one row per shipment

**The setup.** `raw_d5_shipments` carries 16 rows for 14 shipments. S008 and S009 each
appear twice — once in batch 1 (`IN_TRANSIT`), once in batch 2 (`DELIVERED`). S009's
restatement also **corrects the cost**, 13.50 → 11.75, so a missing dedup is visible in
`shipping_cost_usd` and not only in the counts.

The problem states the grain of `stg_d5_shipments` in bold, states the row counts (9 / 16),
and states "a shipment is represented by its latest feed row". This trap is a *reading*
failure, not a knowledge one — which is the point, given the `[general] substituting a
blanket rule for case-by-case reasoning` entry (three occurrences). Day 2 already required
a latest-row-per-key dedup, so the technique is not new.

**What a naive solution does.** Treats `stg_d5_shipments` as the shipment dimension and
aggregates it directly.

**Resulting table — no dedup, single join, `count(*)` (this is trap 3 and trap 4 together,
the most likely combined failure):**

| ship_date | warehouse | got | expected |
|---|---|---|---|
| 2026-06-01 | WH-A | 4 / 4 / 46.50 / 7 / 5.250 | 2 / 2 / 21.50 / 7 / 5.250 |
| 2026-06-01 | WH-B | 2 / 0 / 30.00 / 6 / 4.150 | 1 / 0 / 15.00 / 6 / 4.150 |
| 2026-06-02 | WH-B | 4 / 1 / 37.25 / 12 / 6.900 | 2 / 1 / 19.75 / 12 / 6.900 |
| 2026-06-03 | WH-A | 6 / 4 / 68.50 / 10 / 16.150 | 2 / 2 / 24.25 / 7 / 9.650 |
| 2026-06-03 | WH-B | 1 / 1 / 9.50 / 2 / 1.500 | *correct* |
| 2026-06-03 | WH-C | 2 / 1 / 25.25 / 8 / 6.000 | 1 / 1 / 11.75 / 4 / 3.000 |
| 2026-06-04 | WH-A | 3 / 0 / 48.00 / 8 / 6.250 | 1 / 0 / 16.00 / 8 / 6.250 |
| 2026-06-04 | WH-B | 1 / 1 / 12.00 / 0 / 0.000 | *correct* |

Six of eight rows wrong, all six tests green.

**What catches it:** cell comparison only.

## Trap 4 — the fan-out: header-grain sums over line-grain rows

**Fifth occurrence** of the escalated blindspot `[modeling] counting at a grain that is
not the entity being counted` — Day 1 (null-padded rows counted), Day 2 (dedup side),
Day 3 (`subscriptions LEFT JOIN usage_events`, 8 wrong cells), Day 4
(`payouts LEFT JOIN payout_lines`, three measures inflated, warned about in the problem
text and hit anyway).

**Why it is not defusable by `count(distinct)` this time.** Day 4's inflated measures
included counts, so `count(distinct payout_id)` would have rescued half of it. This day
the exposed measure is `shipping_cost_usd`, a **header-level amount summed once per
shipment**. `distinct` cannot rescue a sum. The counter-measure has to be structural:
aggregate the lines to shipment (or to the grain) *before* joining, or aggregate the two
sides separately and join the two aggregates at (`ship_date`, `warehouse_code`).

**What a naive solution does.** Dedups correctly, filters cancelled correctly, uses
`count(distinct shipment_id)` for the counts — and still writes
`sum(shipping_cost_usd)` over `latest_shipments LEFT JOIN items`.

**Resulting table — dedup right, fan-out wrong:**

| ship_date | warehouse | `shipping_cost_usd` got | expected | line count of the shipments |
|---|---|---|---|---|
| 2026-06-01 | WH-A | **46.50** | 21.50 | S001 has 3, S002 has 1 |
| 2026-06-01 | WH-B | **30.00** | 15.00 | S004 has 2 |
| 2026-06-02 | WH-B | **37.25** | 19.75 | S005 has 1, S006 has 3 |
| 2026-06-03 | WH-A | **48.50** | 24.25 | S008 has 2, S010 has 2 |
| 2026-06-03 | WH-B | 9.50 | 9.50 | S011 has 1 — correct by accident |
| 2026-06-03 | WH-C | 11.75 | 11.75 | S009 has 1 — correct by accident |
| 2026-06-04 | WH-A | **48.00** | 16.00 | S012 has 3 |
| 2026-06-04 | WH-B | 12.00 | 12.00 | S013 has **0** — correct by accident |

Every other column is correct. **Five of eight rows wrong in exactly one column**, and
the three right ones are right only because those shipments happen to carry at most one
line. Same shape as Day 4, where SL03 and SL04 hid the bug.

All six tests green.

**The intervention this day** is not a test — it is `## Grain plan` in `notes.md`, one row
per measure, required *before* the `from` clause is written, because the Day 4 digest
concluded the gap is sequence rather than knowledge. **When grading: check whether the
grain plan was filled in, whether it names `shipping_cost_usd` as header-grain, and
whether the SQL then matches what the plan says.** A correct mart with an empty grain plan
is a partial pass; a grain plan that names the header grain correctly next to SQL that
fans out is the most informative outcome of the day and must be called out.

Debrief question 4 makes him write the missing reconciliation test after the fact.

## Trap 5 (minor) — `CASE WHEN` where the spec needs `WHERE`

**The setup.** WH-C on 2026-06-02 has exactly one shipment, S007, `CANCELLED`. The problem
states that an all-cancelled (date, warehouse) pair produces **no row at all**.

**What a naive solution does.** Handles the cancellation with
`count(*) filter (where status <> 'CANCELLED')` / `sum(case when ... else 0 end)` instead
of excluding cancelled shipments in a `WHERE` before the `group by`.

**Result:** a 9th row, `(2026-06-02, WH-C, 0, 0, 0.00, 0, 0.000)`.

**Test that catches it: V5**, `shipment_count >= 1`. Fails on both runs — this one is
caught on run 1, before the incremental question is even reached.

Secondary damage if the `WHERE` is missing on the item side too: cancelled shipments' item
lines (I005/I006 on S003, I013 on S007, I023/I024 on S014) leak into `item_quantity` and
`total_weight_kg` for rows that otherwise look fine.

Same family as trap 3 — `[general] substituting a blanket rule for case-by-case
reasoning`. `sum(case when …)` is the habitual shape; here the spec asks for row exclusion,
not zero-substitution.

## Trap 6 (minor, self-announcing) — missing `is_incremental()` guard

Writing the watermark filter without wrapping it in `{% if is_incremental() %}` makes run 1
reference `{{ this }}` before it exists. On a clean `practice.duckdb` this is an immediate
runtime error naming the missing relation. It costs one minute and teaches the guard, so it
is recorded but not weighted.

The related silent version: `--full-refresh` on run 1 is in the problem's command block, so
a stale relation from an earlier attempt cannot quietly feed the filter.

## Not traps — do not score these as defects

- `unique_key='ship_date'` versus `unique_key=['ship_date','warehouse_code']`. Under the
  adapter default (`delete+insert`) and a window defined on `ship_date`, **both are
  correct for this data** — the delete removes whole dates and the insert restores them
  in full. Debrief question 2 asks him to construct the batch where they differ. Grade the
  reasoning, not the choice.
- Building an `int_d5_*` model versus a CTE. Both fine; the problem says so.
- Deduping with `row_number()` versus `qualify` versus a `max(updated_at)` semi-join.
  All fine.
- `on_schema_change` value. Any explicit value is acceptable; the requirement is that it
  was chosen rather than inherited, and justified in `notes.md`.
